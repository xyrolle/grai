# Design

grai compiles translation catalogs into plain functions and their type declarations. These are the decisions, each with its reason.

## Goals

The reference workloads are two production SvelteKit apps: app A with 6,379 keys × 3 locales (about 19k messages), and app B with 13,326 keys × 3 locales (about 40k messages).
- A full compile takes well under a second on either.
- An edit to one message reaches the output in milliseconds.
- No network, no plugins, and no TypeScript run.
- The browser gets only its own locale's words.

## Catalogs and config

- **Catalogs are the inlang message-format JSON, one file per locale,** so existing Paraglide catalogs compile unchanged. `$schema` is ignored.
  - **A locale's messages can be split across files,** with `"catalogs": ["messages/{locale}.json", "messages/admin/{locale}.json"]`, so an area of an app, or the team that owns it, keeps a file of its own. A key is still one message per locale: a key in two files of one locale is a compile error naming both, as either could be the one that ships. `add`, `rename`, `seed` and `merge` write a key back to the file it is in; a key a locale lacks goes in its file at the place of the base locale's that has it, and a new key goes in the first file. One of the files may be empty, as long as the locale has messages. With one path, a locale's one file is its catalog, as before.
- **An object of messages nests keys.** A message's key is the names of the objects it is in and its own, joined by `_`: `{ "cart": { "title": … } }` holds `cart_title`. That's how `grai import` names a nested source key, and how Paraglide exports one, so the call is `m.cart_title()` either way. As in the format, a message is a string or an array, and any other object holds messages.
  - Two paths that name one key (`cart.title` and `cart_title`) are an error in their catalog, and so is a message with variants written without its array.
  - The joined key must be a key name like any other, so `cart.item-count` is an error naming its path.
- **The constructs are a deliberate subset:**
  - text and `{name}` placeholders;
  - literals in braces: `{|Gmail|}` shows its text, which a translator gets as a code to place and not to translate, and a number literal is formatted by a number function or `:relativetime` (`{|1000| :number}`, `{1000 :integer}`), in each locale at run time;
  - markup: `{#tag}…{/tag}` and `{#tag/}`, with options (`href=|/terms|`, `rel=$rel`) and attributes (`@translate=no`, `@hidden`), a quoted value holding any text, braces too, with `\` escaping the next character;
  - variants: `declarations` (`input x`, `local y = x: plural`, `local y = x: plural type=ordinal`, and a `:number` or `:integer` local to select on), `selectors` and `match`, with `*`, several selectors, and `""` for a message without selectors;
  - formatting: `:string`, `:number`, `:integer`, `:percent`, `:offset`, `:currency`, `:unit`, `:relativetime`, `:list`, `:datetime`, `:date` and `:time` with their options, in a placeholder (`{x :number}`) or as a local (`local y = x: number`). `useGrouping` takes Intl's `always`, `auto` and `min2`, and `true` and `false` as Paraglide writes them, which Intl takes as booleans and not as their text; MessageFormat 2's `never` is `false`;
  - the escapes `\{`, `\}` and `\\`.

  Anything else is a compile error that names the construct, rather than an approximation. That covers functions grai does not have, such as a project's own, an option's value taken from an input other than a currency, a unit or a time zone (such as `style=$style`), plural options other than `type`, a local made from another local, a literal a date or list function would read, and selecting on a date, or on a number whose notation or style shows more than its digits (`docs/followups.md`). So is a message whose program would not mean what it says: a name declared twice, which MessageFormat 2 also refuses, and a selector that is no name or is listed twice.
- **A key is a JavaScript identifier, unique ignoring case.** It is the export name, and the last segment of its per-key import path. On a case-insensitive file system, two such paths that differ only in case are one file.
- **A key binds its own name unless its module's code calls that name.** The code calls the runtime's functions, plurals.js's and formats.js's by their own names, and globals such as `String` and `Number`, so a key named `text` or `String` would take the name from the code that calls it. Each compiled key records every name its code calls; a module binds a key that takes none of its module's names as `export const key = …`, and any other to `$` and the key, exported under the key (`const $text = …; export { $text as text }`). A key that collides with nothing costs nothing. Binding every key to `$` and its name was measured and not adopted: a server build 8.9% larger on app A and 11.6% on app B, 3–13% more heap, the compiler's unbundled output 23–30% larger.
- **Every key is in every locale.** A key missing from a locale is one compile error naming the locales that lack it and the `grai add` command that adds it to them. A missing translation would otherwise ship as a failed import or as another locale's words.
  - **A locale can fall back to another of its language,** with `"fallbacks": { "en-GB": "en" }`: a key its catalog lacks then compiles from the other's message, which costs nothing at run time, and its catalog can hold only the messages that differ, or none. Never to another language, as i18next allows, which would show that language's words, and never by tag alone, as Paraglide does, so a locale stays strict unless the config says otherwise. The base locale takes no fallback, as its catalog is where every key is declared.
- **The config is one JSON file, `grai.config.json`:** `locales`, `baseLocale`, `catalogs` (`"messages/{locale}.json"`), `outdir`, the `strategy` with the places it reads: its cookie's `cookieName`, `cookieMaxAge`, `cookieDomain` and `cookieSameSite`, `localStorageKey` and `queryParameter`; `switch`, `tests`, `identicalToBase` and `fallbacks`. JSON is read without executing code, so the CLI, Vite and Next read the same file the same way.
  - **Editors complete and check it through `config.schema.json`,** which the package ships and a config names with `"$schema": "./node_modules/@xyrolle/grai/config.schema.json"`.
- **A pseudo-locale is compiled for development, and never for a build.** `pseudoLocale` names a locale, such as `en-XA`, made from the base's messages at compile time:
  - each letter is accented, the text grows by about 35% in whole words, and each message is in brackets, its placeholders and markup as the base writes them;
  - a page in it shows which text bypasses the catalogs, which layout breaks with longer words, and where a text is cut, with no translator involved;
  - it takes the base's variants, so it must have the base's plural categories;
  - `grai watch` and the Vite dev server compile it. `grai compile` and a Vite build leave it out, so it never ships, even when a build runs over a dev server's output.
- **Nothing is fetched and nothing is loaded from elsewhere.** grai's parser is the format's only reader, so a compile cannot depend on the network.

## Output layout

```
<outdir>/
  messages.js   messages.d.ts    `m`, the namespace of keys.js
  keys.js       keys.d.ts        every message, as the re-exports of the shards
  runtime.js    runtime.d.ts     the runtime's API, which apps import: re-exported from internal.js
  internal.js   internal.d.ts    the runtime's anchor: all of runtime-<hash>.js; apps never import it
  server.js     server.d.ts      the request middleware; client code never imports it
  testing.js    testing.d.ts     the locale a test renders in; a build refuses it

  keys/<n>-<hash>.js  .d.ts      a shard: about 512 keys
  keys/g<n>-<hash>.js .d.ts      a group of keys an adapter saved (Next's routes), when there is one
  keys/<n>.d.ts.map              its declarations' map to the keys in the base catalog
  runtime-<hash>.js   .d.ts      the runtime, the same for every project, but for its config's name
  config-<hash>.js               the project's locales and strategy, which the runtime reads
  plurals-<hash>.js              each locale's plural rules, compiled from CLDR
  formats-<hash>.js              the Intl formatters messages call, when any does

  package.json                   its modules are ES modules, and only server.js has effects
  .grai/manifest.json            what the output was compiled from, and its files
  .grai/build                    the build a watcher saved, which the next one starts from
  .grai/groups.json              the groups of keys the output holds each in a module of its own
  .gitignore                     `*`: the output is compiled, never committed
```

The first five are the entries, which apps import by name. Every other file is named by a hash of its content, so a compile never replaces one (see "Incremental compiles and atomic output").

- **The output has Git ignore it, through a `.gitignore` of its own.** Git, Prettier 3, Biome with its VCS ignore, and editors' searches then skip it with no setup. ESLint's flat config does not read `.gitignore`, so a project lists the outdir in its `ignores`. There is no option to commit the output, as neither reference app does. The outdir is grai's alone, so the config rejects one that holds the config or a catalog, which the `.gitignore` would hide.
- **The outdir is a package boundary of its own: its package.json says `"type": "module"` and `"sideEffects": ["./server.js"]`.**
  - Its modules are ES modules, whatever the project's package.json says. A CommonJS project's Node loaded them by syntax detection, with a warning at each, and now loads them as they are. TypeScript reads their declarations as ES modules too: a CommonJS project checked under `module: node16`, which models a Node that cannot `require()` an ES module, gets an error where it imports the output, as it would at run time on such a Node; `nodenext` models Node 22 and later, which can.
  - Only server.js does anything as it loads (it binds the request's store), so a bundler that reads `sideEffects` leaves out a module of keys no code reads, and keeps the one whose key the code calls, its check of the runtime with it. `next dev` then compiles, in each layer, the modules of the keys that layer reads, where it compiled every shard (`test/next-dev.test.ts`).
  - Every module of the output imports only modules of the output, by relative paths, and Node's builtins, so nothing in it resolves against the package.json (`test/outdir-package.test.ts`).
- **On disk, a few modules hold every message.** Node, scripts and tests load them as they are, and the output is a few dozen files whatever the key count. Per-key files would cost every install, editor index and file watcher, two files a key: 26.7k for app B.
- **The keys are split into shards by a hash of their name**, a power of two of them so that a key moves only when the key count doubles. An edit then writes one shard of about 512 keys, under its new name, not the whole catalog's output. TypeScript and editors read that shard alone.
- **Saved groups of keys come first, each in a module of its own; the other keys are in their shards.** `.grai/groups.json` lists groups of keys that are read together, which an adapter saves from the app's code (only Next's does, below). Every compile, a build's and a watcher's alike, places a key in its group when one holds it, so `next dev` and `next build` write the same output for the same state. With no groups saved, the output is the shards alone, as before; Next's watch reads them for a fresh clone's first start when that costs the start little (below). Groups out of date cost speed, never a key: a key no group holds, as one added since, is in its shard, and keys.js exports every key whatever the groups. A group's declarations are beside its module under the same name, as a shard's are, since TypeScript takes a module without them into a project that checks JavaScript.
- **Per-key import paths map to keys.js with one line, never a file per key.** An app that imports `import { key } from "…/messages/key.js"` maps the pattern in its package.json `imports` (`"#i18n/messages/*": "./src/lib/i18n/keys.js"`). Node and TypeScript resolve every key's path to keys.js and its declarations, and a key that does not exist is a type error at the import. The Vite adapter resolves the same paths itself.
  - **A key's path names its key by its last segment, case and all, and imports that key:** `…/messages/Title.js` is the key `Title`, never `title`. Each of grai's resolvers reads the key there, and so can a tool that walks an app's imports, such as one that finds the keys a route reaches: outside them every key's path resolves to keys.js, which names none. Keys are unique ignoring case (above), so no two keys' paths differ only in case; and as no file stands for a key, a path in another case than its key's names a key no catalog has on every file system alike.
  - **A file per key was measured and rejected.** A `.js` and a `.d.ts` per key, each re-exporting the key from keys.js, made app B's output 26,762 files instead of 109. Its compile went from 194 ms to 2,758 ms cold, from 2.9 to 37.9 ms with nothing to do, and from 38.6 to 102.9 ms for one edited message (medians of three, load 13–21).
  - **Each runner makes a key's module as it resolves the key's path, rather than a file making it.** Grai's Vite plugin does in a build and a test run, and `@xyrolle/grai/register`, loaded with `node --import`, does in Node: a resolution hook on `module.registerHooks` gives each key's path a module that reads the key from keys.js. A test that mocks one key's path, with Vitest's `vi.mock` or node:test's `mock.module`, mocks that key and no other. On app B, with a page importing 300 keys by path:
    - the hook's 300 modules add 21 ms to Node's import of the page, 67 ms against 46, and 34 ms with Node's compile cache warm, 72 against 39, as the cache keeps no module a hook makes (medians of five, load 12). A process without the hook loads as before;
    - a `.d.ts` per key, re-exporting its shard, made 13,441 files and a 1,453 ms cold compile against 207 ms, and an edit 356 ms against 240 (medians of three, load 12–19);
    - a `.js` and a `.d.ts` per key made 26,767 files and a 2,801 ms cold compile against 214 ms, and Node's import of the page 96 ms against 66.
  - **TypeScript sees one module for every key's path.** An editor's auto-import offers keys.js rather than the key's path, since TypeScript cannot turn a pattern that maps to one file back into a key's path.
- **A production build splits by key, from memory.** Measured with Vite 8.3 (Rolldown) and Rollup 4.52, on two entries that use two keys each, one key shared:
  - one module of keys: static member access on its namespace drops the unused keys, but every key used anywhere lands in one shared chunk, so each route carries the others' words;
  - one module per key: each entry's chunk carries only its own keys, and the shared key gets a chunk of its own.

  So the Vite adapter builds one module per key from the compiler's model, and `keys.js` and the per-key paths resolve to them. They are never files, and the adapter's build test pins both results.
- **A server build puts the keys that two or more entries use in one chunk, and leaves each other key in its entry's chunk.** A server loads each chunk as a module of its own. Split by the entries that use them, the keys that several pages share become a chunk per set of pages: 2,668 modules for 64 pages that use app A's keys, six in ten keys on one page and the rest on 2 to 16, against 65 (`server-pages`). Every key in one chunk would make each page load every key, which costs workerd more than its small modules do. The browser keeps its chunks by the entries that use them, so a page downloads only its own keys.
- **Dev serves one module.** A dev page then requests every message as one module, whatever the key count, and every per-key path resolves to that same module.
  - **Its text keys are one JSON string, which a page keeps beside the strings parsed from it.** An object literal and an export statement per key cost about 150 ms more of a cold start on app A, in Vite's SSR transform and V8's compile. A page pays for the JSON instead: the JSON text is 3.4 MB of app B's 14.9 MB. Built with an object literal and an export statement per key, app A's page keeps 7.1 MB rather than 8.0 MB, and app B's 12.3 MB rather than 14.9 MB (`hmr`). A dev server pays its start every time it runs. A page keeps 351–361 B a message over a page with no messages, and `hmr` holds it to 400 B (`docs/runtime.md`). That is about a seventh of what Paraglide's dev page keeps.
  - **The module makes its messages in a function of its own.** V8 compiles a function whose loop runs long. When the loop over every key was in the module's top level, V8 compiled the whole top level, and the page kept that code: 2.4 MB, which took app B's page from 14.9 MB to 17.3 MB.
  - **That module has an id of its own, `\0grai:keys`, not keys.js's path.** Vite's module graph ties a module to the file of its id, and its watcher takes each write of keys.js, which every compile makes for Node and TypeScript, for a change of the module: it would mark the module and every importer changed, and the server's runner would evaluate the app again on its next render, where an edit's patch is all it needs.
  - **A test run is the exception.** In Vite's test mode, which Vitest runs, each key's path resolves to a module of that key alone, a re-export from keys.js. A test that mocks one key's path then mocks that key and no other, and an edit still reaches the key through keys.js.
  - **A page keeps one module because a module per key costs it a request each.** On app B's catalog, a dev page importing 300 keys by their paths loaded in 445 ms rather than 346 ms the first time, and in 103 ms rather than 54 ms on a reload (medians of three, load 13).
  - **A test run pays about the same per key's path**, the price of mocking one key. Through the server's module runner, as Vitest loads a test, the 300 imports took 897 ms rather than 691 ms.
  - A missing key's path resolves to a module whose one export throws a `GraiError` naming the key when called, and the plugin reports the import in the overlay. The import itself succeeds, because a failed import would set off Kit's stale-deployment reload.
  - A key the build has still resolves to keys.js outside a test run, so a page that imports hundreds of keys by path loads no module more for them (app B has 23,379 such imports in 1,924 files). The plugin resolves these paths before Vite does, since Vite's resolver would take them straight to keys.js.
  - It keeps each per-key import's importer, so that a build that adds or removes the key has the importer resolve it again: an added key reaches keys.js, and a removed one the module that throws.
- **The per-locale variants of the message modules exist only in memory too.** They have the same exports, with one locale's function each, and the bundler adapters build them from the compiler's model.
- **The output brings its own runtime.** `runtime-<hash>.js` is the package's runtime module, with its import of the config naming the output's `config-<hash>.js`. The output imports nothing from `@xyrolle/grai`, so it runs wherever the app's code runs: a Worker, a script, or a server bundle that leaves out its dependencies.

### The browser's locale

The server picks the page's locale. The client's locale is the page's `<html lang>`, which the server writes, so the page hydrates in the words it was drawn in. A production client build loads only that locale's variants of the message modules it uses.

They come through an import map, which keeps the framework's single client build (`docs/runtime.md`):
- **The Vite plugin puts the key modules in chunks of their own,** by what loads them, under a directory `grai` within the one the bundler would have used (Astro's `_astro/` gives `_astro/grai/`, Kit's `_app/immutable/chunks/` gives `_app/immutable/chunks/grai/`). Within it, because hosts serve that directory as immutable and nothing beside it: `@astrojs/node` caches `/_astro/*` for a year and a sibling `/grai/` not at all. The runtime has a chunk of its own, so a message chunk holds keys and nothing else.
- **grai chunks the keys by what loads them.** The keys the same contexts load form a set, and one chunk per set loads exactly the keys a page uses. But most sets are a key or two: on app B, 1,909 sets made a page load 80 message chunks (median), each a request, a preload link, and imports and exports that compress poorly alone. So:
  - A key's contexts are the pages whose first paint reaches it and the later imports that do. A page is the entries its first paint loads together: a framework's adapter names them (`pageEntries`), and without one each user entry is a page. SvelteKit loads a page's layouts with it, which the bundler cannot know, so a key a layout and a few of its pages use goes with the layout's own.
  - Two sets share a chunk when the requests that saves, at 600 bytes a request, outweigh the bytes it has their other contexts load in vain. Keys a first paint needs and keys only later imports need never share a chunk.
- **A key's reach is read from the bundler's graph (`ctx.getModuleInfo`), as the bundler takes modules in.**
  - A build takes a per-key path to the key's own module, so the key's importers are the modules that use it.
  - A module that reads the namespace, `m.key`, through any of the app's re-exports, reaches the keys it reads, which the plugin's check reads from its code as it ships. One that reads it by a computed name, `m[name]`, may read any key, and reaches every one. keys.js, which re-exports every key, reaches none: through it, every page that imports `m` would reach them all.
  - A module that only re-exports, such as an index of a directory's modules, links an importer only to the modules that hold the names it takes, and to those whose side effects the bundler keeps. A module that its package's `sideEffects` or a plugin says has none, the bundler leaves out for an importer that takes nothing of it, and so does a key's reach.
  - `m` passed whole (`fn(m)`) and a named import of a key from keys.js are not followed. A key read only so is reached from its other readers, and a page that reads it so loads its chunk as one more request.

  On app A, which reads every key through `m`, and some through modules an index re-exports, the graph told no key's reach, and Rolldown's entry sets, pooled at 4 KB, chunked them: a page loaded 19 message chunks (median), 1,245 KB of Russian, brotli, summed over 73 pages, and 34.3 KB on the largest. Read as above, 10 chunks a page, 1,027 KB, 28.5 KB on the largest; with SvelteKit's pages, 7 chunks and 1,009 KB. Paraglide's per-locale build, each page's keys bundled into one file: 1,105 KB, 30.1 KB. Without seeing through the index, a page that imported one of its modules' names reached every module it re-exports: with no set merged, pages loaded 49,606 keys for the 29,950 their code reads, every key too many one of those modules'. On app B, which imports each key by its own path, with SvelteKit's pages from its routes, a page loads 13 message chunks (median), in 846 KB of English and 1,210 KB of Russian, against Paraglide's tuned setup's 21 in 862 and 1,183 KB. Grouping takes about a second of a 13,000-key build.
- **Key modules import the output by `grai:output/`, a prefix of grai's, not by its path.** The plugin resolves it to the output's real path, so a project reached through a symlink holds one runtime, and a key module's code is the same wherever the project lives.
- **The formatters stay in the runtime's chunk.** A chunk of their own would spare a page without formatted messages their bytes, for one more request on every page with one. App A has no formatted message, and app B's formatters take 223 bytes brotli.
- **Each message chunk has a copy per locale,** when the app asks for them with `localeChunks`, under the sibling `grai-<locale>/`, with the same file name, imports and exports. Each key's call keeps only its locale's variant. The runtime reads a list too short for the locale's position as holding the only variant there is. On a page that is the page's variant: every call there renders in the page's locale, and the import map that loads a locale's copies comes from the same pick as the `<html lang>` the runtime reads. The test for a short list is the bounds check the read already makes, so a call takes what it did: in one Chromium page, the two runtimes' calls alternating, within 0.5 ns of each other either way on calls of 10–15 ns. The copies used to pad each call with an argument per locale before the page's, so that the runtime could read a copy at the locale's position. That padding cost app B's Russian copies 1.7% brotli summed over its 89 pages (20.8 KB of 1,197 KB, with the build's hashes made equal), its Romanian 0.6%, and app A's English, its third locale, 1.0%. Placing a copy's variant at the page's position once, as its message is made, would leave the call as it was. But it costs every message an array as the page loads, and the runtime 1,070 B, over its 1,061 B budget, where this read takes it to 1,043 B. A sibling, not a subdirectory, so the copies' relative imports reach the same shared chunks. They are off by default: only an adapter that writes the import map reads them, and without one they are dead output, uploaded with every deploy.
- **The server writes the import map,** from `…/grai/` to `…/grai-<locale>/`, and points the page's `modulepreload` links at the copies, as browsers apply no import map to `modulepreload`. Without the map a page still works, with every locale's words. `@xyrolle/grai/sveltekit`'s `handleLocale` does both ("SvelteKit" below). `@xyrolle/grai/nuxt` writes them for Nuxt, in the import map Nuxt writes for its entry.

### A page no server draws

A static site, an Electron app or a browser extension has no server to pick the locale. The Vite plugin writes a locale script into each page it builds or serves, which picks it in the page:
- **One strategy for the server and the page.** Each reads, in the config's order, the places it can see: the server the request's cookie, query parameter, path and `Accept-Language`; the page its cookie, `localStorage`, query parameter, path and `navigator.languages`. A page a server drew and a page a static host served then pick the same locale. A list per side would let the two disagree.
- **An inline classic script, ahead of every module script and module preload,** after the tags before them, such as `<meta charset>`, which must stay within the page's first 1024 bytes. The import map must be in place before any module loads, which no module can do, and the runtime reads `<html lang>` when it loads.
- **A language is matched by one function, the server's.** `server.js`'s `localeReach` gives the locales a language range reaches, and the plugin writes the same function's source into the script, so the two cannot drift. The function refers to nothing outside itself, and the script calls it with the locales and takes the nearest locale each of the browser's languages reaches.
- **The script holds the code of the places the config's strategy reads, and nothing else.** Each place has a function of its own that makes its reader, and the plugin writes the readers of the strategy's places alone, in its order, with the settings they read, and `localeReach` only for a place that matches a language (`query`, `preferredLanguage`). The import map's code goes only into a build that copies the message chunks. A page with a cookie strategy and copies holds 451 bytes brotli of script, where one with every place's code held 988, which put grai's runtime in a page behind Paraglide's (`bench/library-bytes.mjs`: 2.0 against 1.8 KB; 1.4 KB with this).
- **The `<html lang>` a page is built with is only its default.** Vite's template writes `<html lang="en">`, which says nothing of the visitor, so the plugin names the page's built `lang` in the script's `data-grai-lang`, and the script picks the locale while `lang` is still that one, keeping it where no place of the strategy names a locale. A server or a prerender that writes another of the locales in its place drew the page in it, and the page keeps it.
- **The script only reads.** A locale found in `?lng=` is not stored, so following a link does not change a visitor's choice. `setLocale` keeps a choice in every place the strategy lists, the query parameter among them, so a stale `?lng=` cannot win over a newer choice.
- **In a build with `localeChunks`, the script writes the import map to the locale's copies and preloads the copies the page's entry imports.** Without it, the page loads the message chunks every locale shares, as the copies are opt-in for every adapter. The plugin leaves the shared message chunks out of the page's own preloads, through `build.modulePreload.resolveDependencies` (after the app's own, if it has one), as they would fetch every locale's words. Vite's preloads of a dynamic import resolve through `import.meta.resolve`, which applies the import map, so a module the page imports later loads the copies too.
- **The script is the same for every page and every build of a project.** Each page's chunks are in its `data-grai-chunks`, which a Content Security Policy's hash does not cover. Its hash, and those of the import maps it writes, change only with the config, `localeChunks`, the base or grai, and the build's log names them, for a policy that allows scripts by hash. Under Vite's `html.cspNonce`, the script carries the nonce and gives it to the import map and preloads it writes.

**Every client rule is the same in every build, dev and tests included, so nothing fails only after deploy.** On the client, a forced `{ locale }` must be the current locale. Any other throws a `GraiError` (`locale-not-loaded`) naming both locales, and in dev the key too. A build leaves key names out of the page: on app A they would add a third to its gzipped message bytes, and the call site in the stack names the key.

### A Svelte component reads a message without inputs as its string

`@xyrolle/grai/svelte`'s plugin is `@xyrolle/grai/vite`'s, and in the client build it also rewrites each component: a call of a text key with no arguments, `{m.title()}`, or `{title()}` of the key's own import, becomes a read of that key's string in the page's locale. The string comes from a module of its own (`grai:text/title`), whose `pageText(…)` picks the page's locale once, as the module is evaluated.
- **Svelte draws an imported value as plain, and treats a call as possibly stateful.** It gives each message call a derived signal and runs it as the page hydrates; a string it sets once. On a page of 2,000 calls with app A's catalog, built by Vite through both plugins, the strings hydrate in 16.2 ms against 24.3 ms for the calls at a 4× CPU slowdown, two-thirds of the way to text inlined into the template (12.9 ms, `svelte-texts`).
- **Text is not inlined into the template.** On the synthetic page it would close the rest, but on app A's real pages it hydrates within the noise of these strings, −9% to +4% at a 4× slowdown, for 1–3% less JS and a copy per locale of every component chunk with such a text, 744 more files (`docs/runtime.md`).
- **The string modules go into the message chunks, and into their copies per locale,** like the keys, so a page still loads only its locale's words.
- **A call is rewritten only where it is certain to be grai's.** Names are followed to keys.js through the app's own re-exports, as the bundler binds them, and a key's own path to the key's own module, which a build resolves it to. A component that declares one of those names again, as an `{#each}` item or a parameter, is left as it is, and so are calls with arguments (a forced locale among them), markup, values and dynamic keys.
- **The server build reads the same calls as a property:** `.text` of the key's text module, an object `requestText` makes from the key's variants, whose getter reads the variant of the request's locale. Every text's object has the same class, so a page's reads of all its texts share one getter. A getter of its own per text, which called the key, made a server render of the synthetic page about a fifth slower (`bench/ssr.mjs`: 116 against 143 µs in `ru`, 121–128 against 157–166 µs in `ro`). Under `experimental.async`, Svelte takes a call made after a component's `await` as writing whatever it touches, and every later read of the namespace as waiting on that await. A call kept on the server then compiles into blocks of its own that the client's string lacks, and Svelte draws the page again instead of hydrating it. A property read waits on nothing, as the string does, so both sides compile the same blocks.
- **Dev keeps every call,** since it patches a message's function in place, and so does `"switch": "live"`, whose page re-renders in another locale.
- **The plugin reads each component after Svelte's preprocessors and before its compile,** so `grai()` is listed before `sveltekit()`. Listed after, the build fails and says so.

### Switching locale on the client: a choice

Tests switch the locale within the page, and so do many apps, without a reload. A production page holds only its locale's words. The config's `"switch"` picks one of two designs, each the same in every build:

- **`"reload"`, the default: no switch within the page.** `setLocale(locale)` keeps the choice and reloads or navigates, so a page keeps its words while it lives. `setLocale(locale, { reload: false })` only keeps the choice, for the page's next load: the page's locale, its `<html lang>` and its messages stay as they are, as it holds no other locale's words. A strategy that keeps a choice nowhere, the browser's languages alone or nothing, would load the page in its old locale again, so there `setLocale` in a page throws (`locale-unkept`) rather than reload to no effect.
- **`"live"`: load, then switch.** `setLocale(locale, { reload: false })` imports the target locale's variants of the message modules the page holds, then switches, and the app re-renders. It is not built yet, so the config refuses `"live"` (`docs/followups.md`).
  - In that mode it returns a promise that settles once the switch is done.
  - `setLocale(locale)` keeps reloading and returns nothing.
  - In dev and tests, where every locale is loaded, the promise settles at once.
  - The adapters must know which message modules a page holds.

## The generated functions

```js
// keys/3.js, a shard, for locales ["en", "de"]
import { message, text } from "../runtime.js";
import { plural_en } from "../plurals.js";

export const cart_title = /*#__PURE__*/ text("Your cart", "Ihr Warenkorb");

export const cart_items = /*#__PURE__*/ message(
	(i) => (plural_en(i["count"]) === "one" ? `${i["count"]} item` : `${i["count"]} items`),
	(i) => `${i["count"]} Artikel`,
);
```

- **One plain function per locale, in `locales` order.**
  - `message` returns `(inputs, options) => variants[index of (options?.locale ?? the bound locale)](inputs)`: one shared dispatcher, not a copy per key, in `keys.js` and a page. A server build differs (below).
  - **A dispatch of each key's own was measured and not adopted.** The shared closure's call of the locale's function sees every key's function and goes megamorphic. A dispatch in each key's own code keeps it monomorphic: in a client build, with the page's locale copies in Chromium, a call with inputs takes 9.8–11.7 ns against 18.2–21.7 ns on apps A and B, and Paraglide's given `{ locale }` 11.9–16.4 ns. But a page of 2,000 calls saves about 1.5 µs a render that way, and pays more at every load. A dispatch the runtime makes from each key's code, `dispatcher((v) => (i, o) => variantFor(v, o)(i), […])`, compiles that arrow for each key as the page evaluates, 0.2–0.4 ms more on that page, about 1 ms at a 4× CPU slowdown. An array and an arrow of each key's own call nothing as the page evaluates, but each key's names are its own and compress badly: 9.7% more message bytes with brotli on app A, and 0.5–0.7 KB more on that page. A view that draws thousands of calls again and again would gain; a page that draws its messages a few times does not.
  - A message without inputs is a string per locale (`text`).
  - One locale may use a plain pattern where another selects: the German above needs no plural.
- **A message with markup also has `.parts()`**, built the same way. A part is `{ type: "text", value }` or `{ type: "markup-start" | "markup-end" | "markup-standalone", name, options, attributes }`. An option is a literal, or the value of an input or local (a formatted local as its text); an attribute is a literal, or `true` when it has none. The app then decides how markup looks, and translators decide where it stands.
- **Inputs are read as `i["name"]`, not `i?.name`.** The types require them, and the body is repeated in every message function (40k in app B). The brackets keep an app's checkJs clean under `noPropertyAccessFromIndexSignature`, which `@tsconfig/strictest` sets, as the compiled functions take their inputs typed by an index signature. A minifier writes them back as `i.name`, so a browser's bundle does not change; a server build, which is not minified, grows 1%: app A's Vite server build from 2,189,415 to 2,213,025 B. Taking the inputs apart in the parameter, `({ count: _count }) =>`, was the other way: it reads every input a function names on every call, and it is larger minified and slower to load. App A's minified `keys.js` is 1,506,516 B against 1,500,110 B, 2.6 KB more brotli, and loads in 35.7–41.2 ms against 24.3–30.6 ms in a new Node process (`startup`, two interleaved rounds at a load of 14–27).
- **A server build writes its functions as function expressions, `function (i) { return … }`.** V8 parses every arrow function of a module in full when it loads the module, but only pre-parses a function expression, until its first call. A server loads every locale's functions and a request calls few of them, so the Vite plugin's server build loads app A's messages about a fifth faster (`docs/runtime.md`). The browser's modules and `keys.js` keep arrows, which are shorter.
- **A server build's message with inputs switches on the call's locale in its own code:** `function (i, o) { switch (localeIndex(o)) { case 0: return …; default: return …; } }`, each locale's code in its case. Through the shared `message`, one call site calls every key's functions, and the engine stops optimising it. In a request, side by side with the shared dispatcher on the synthetic catalog and apps A and B, a call with inputs takes 23–71 ns against 67–92 ns, and a plural 32–69 ns against 51–98 ns, where Paraglide's given `{ locale }` takes 22–45 ns and 579–679 ns. Text and markup calls stay within the spread between two builds of the same code. A key holds one function in place of one per locale and the dispatcher's closure, so a new Node process loads 0.1–2.1 ms faster and holds 0.4–0.7 MB less, and workerd loads 1–3 ms faster. The first render is 0.8–1.8 ms slower, as a key compiles every locale's code on its first call: a cold start comes out level, and with Node's compile cache warm, the calls win the difference back within 46 renders of a 2,000-call page.
  - **A server build, and messages with inputs, only.** A page loads only its own keys and draws them a few times, so its load would cost more than its calls save (above). A text's call reads a string, which no dispatch slows, and a function of its own per text key doubled the first render. A message with markup spends its call building its parts, and a switch of its own gained nothing.
  - **Not adopted:** a dispatch the runtime makes from a function of each key, an array of each key's functions with a function that indexes it, and a switch that calls a function per locale. Each gives a key another function or binding, and loads 3–16 ms slower.
- **Calls are not replaced after the framework compiled them.** Each locale's function is a pure arrow of its inputs, so a bundler transform could put a call's string in its place, in a build per locale. But Svelte has by then compiled each call as a dynamic expression, and the string stays inside it: on the page of 2,000 calls the strings hydrate in 23.9–24.1 ms against 23.3–24.3 ms for the calls at a 4× CPU slowdown, where `@xyrolle/grai/svelte`'s, put in before Svelte compiles, take 15.9–16.2 ms (`docs/runtime.md`). It would also take a copy per locale of every client chunk that calls a message, 978 more files on app A. Inlining the text into the template, before Svelte compiles it, is not adopted either (above).

## Declarations

```ts
// keys/3.d.ts
import type { Message } from "../runtime.js";
/** Your cart */
export declare const cart_title: Message;
/** {count} item (en, one) … */
export declare const cart_items: Message<{ count: number }>;
```

- **The compiler writes the `.d.ts` files itself, as text, from the same model as the JavaScript.** It never runs TypeScript. Declaration emit through TypeScript takes most of a compile at this catalog size: Paraglide's compile of app A takes 3.8 s, and 32.1 s with TypeScript's declarations (`compile-time`).
- **The runtime's declarations ship as files beside the runtime, `runtime/<name>.d.ts.template`, which the compiler fills with the config's locales.** As strings in the compiler's modules they were 3 KB, gzipped, of every bundle of the compiler, in each adapter's plugin. They are `.template` files because TypeScript reads none: a `runtime.d.ts` beside the runtime's `runtime.js` would be the types the repo's own check takes for it.
- **The types are named in the generated `runtime.d.ts`:**
  - `Locale` is the union of the locales.
  - `Message<I>` is `(inputs: I, options?: { locale?: Locale }) => string`.
  - A message without inputs takes `inputs?: Record<string, never>`.
  - `MarkupMessage<I, T>` adds `.parts(): MessagePart<T>[]`, where `T` is the union of the tags every locale writes. A part named otherwise is a type error, so an app's renderer can map exactly those tags.
  - Messages return `string`.
- **An input's type is what every use of it takes, in every locale:**
  - `number` where a locale counts it with `:plural` or formats it as a number or a relative time, `Date | number` where one formats it as a date, and `readonly string[]` where one formats it as a list;
  - the keys, as numbers and strings (`1 | "1" | …`), where a locale selects on it and lists its values without `*`;
  - `string` where it gives a formatter an option, such as `currency=$code`;
  - `string | number | bigint | boolean | object` where it is shown as text, which is what a template literal turns into text: a symbol has none, and throws in a message's text and in its parts alike;
  - `NonNullable<unknown>` where it is only selected with `*` or given to markup.

  Each use narrows the type, so an input both selected on `1` and `2` without `*` and formatted as a number is `1 | 2`, and one a locale selects on `a` and `b` and another on `a` is `"a"`. Two uses no value suits both of, such as `{x :currency currency=$x}`, which formats `x` as a number and takes its currency from it, are a compile error naming both, so a call that type-checks renders in every locale. A key's inputs are the union over its locales.
- **The doc comment is the base locale's text**, so an editor shows the words at the call site.
- **Go to definition lands on the key in the base locale's catalog.** Each shard's declarations have a declaration map, from each key's name to the line its key is on in the base catalog, and TypeScript 6's tsserver and TypeScript 7's language server both follow it. An edit regenerates the maps only when it moves a key to another line, so a message's new words cost no map.
- **The output's JavaScript type-checks too**, under `checkJs` with `strict`, as an app with it in `src` checks it. `runtime.d.ts` declares what the shards and `server.js` import from the runtime, and `config-<hash>.js` and `plurals-<hash>.js` carry JSDoc types. `server.js` imports `node:async_hooks`, which only Node's types declare, so such an app needs them; Workers, Bun and Deno take theirs from Node's too.
- **The declarations are sharded like the modules.** One file loads a little faster in an editor the first time, but an edit rewrites it whole, so every edit after costs more. A file per key costs the most in `tsc` and in completion alike.

## Selection: plurals and selects

These are MessageFormat 2's rules, restricted to the constructs above:

- **`local n = count: plural` selects the CLDR cardinal category of `count`** for the message's locale, through a function compiled from CLDR's rules for that locale alone. A whole, non-negative count, the usual one, takes a path with the fraction operands folded away; any other count is rounded to three fraction digits first, as `Intl.PluralRules` rounds it, and one that is not finite (`NaN`, `Infinity`) is `other`, as `Intl.PluralRules` gives it. That is 3.4–11.4 ns a call, as plurals.js has the rules, against 112–246 ns for a cached `Intl.PluralRules` (`plurals`), and every locale agrees with `Intl.PluralRules` on 0–10,000, on fractions, on negative counts and on counts that are not finite. The rules are CLDR 48's, from the `cldr-core` package, so a project's categories are the same on every engine; the compile checks the variants against them.
- **`local n = count: plural type=ordinal` selects the CLDR ordinal category of `count`** (`one` for 1st, 21st, `two` for 2nd in `en`), compiled from CLDR's ordinal rules the same way, and Paraglide's `plural` takes the same option. Every locale agrees with `Intl.PluralRules` of type ordinal on 0–1,000 and on fractions. A language whose every count is `other`, as 66 of CLDR's 108 rank (`ru`, `de`) and 34 of its 224 count (`ja`, `zh`), gets a function that returns it without reading the count, so a bundle of it carries no operands.
- **A `:number`, `:integer` or `:percent` local selects as MessageFormat 2's `:number` does.** A key that is a number matches a value equal to it, and a key that is a category matches the value's category: cardinal by default, ordinal with `select=ordinal`, and none with `select=exact`. An exact match comes before a category, so `n=1` is chosen for 1 over `n=one`. `:integer` rounds the value half away from zero first, as it shows it.
  - A key is compared with the value as JavaScript writes the number, which is MessageFormat 2's serialization for a whole number. So, for a local that does not round, `1.0` and `01` can never match, and they are compile errors, as is a fraction under `:integer` or `:percent`.
  - A local whose options round it (fraction or significant digits, `roundingMode`, `roundingIncrement`, `roundingPriority`, `trailingZeroDisplay`) selects on the digits it shows, as `Intl.PluralRules` does given the same options. With `minimumFractionDigits=1`, 1 shows as `1.0`: it matches the key `1.0`, and is `other` in English, where 1 is `one`; the key `1` is a compile error, as no value shows it. The digits are an `Intl.NumberFormat`'s with the local's options, in Latin digits and without grouping, the same in every locale, and the category is the compiled rules' reading of those digits as written, trailing zeros included. Every locale agrees with `Intl.PluralRules` on nine sets of such options, cardinal and ordinal.
  - `signDisplay`, `useGrouping`, `numberingSystem` and `minimumIntegerDigits` only change how a number is written, and a selector takes them. A local in another notation or with a style (`notation`, `style`) is refused as a selector: it shows more than digits, and `Intl.PluralRules` has no category for that.
  - `:percent` selects the same way, always by the cardinal rules, on the whole percent it shows. 0.29 is 29: the decimal point is moved two places, where `0.29 * 100` is 28.999999999999996. 0.014 is 1, as `1%` shows it: the percent is rounded half away from zero, as `Intl.NumberFormat` rounds it.
  - **`:offset` moves its value by its `add` or `subtract`, then selects and shows it as `:number` does with no options,** always by the cardinal rules, as MessageFormat 2 defines it: `local others = count: offset subtract=1`. It is MessageFormat 2's own form of ICU's plural `offset:`, so grai takes it instead of a declaration of its own, and a catalog that uses it stays MessageFormat 2. MessageFormat 2 lets the operand be another local, whose options it keeps; grai takes an input and a literal whole number, which is all ICU's offset needs.
  - A currency, a unit, a date or a time does not select, in MessageFormat 2 or in grai.
- **A selector on an input matches a key when `String(value)` equals it.** That is MessageFormat 2's string selection, so `1` and `"1"` both match the key `1`.
- **A `:string` local selects as MessageFormat 2's `:string` does:** a key matches when it and the value's text are the same in Unicode's NFC, so `café` matches whether the value writes é as one character or as e and an accent, and two keys NFC writes alike are a compile error. Each call normalizes the text once. A selector on the input itself, the inlang format's own, compares them as written, as Paraglide does. `{name :string}` shows a value as `{name}` does, and the local shows its input's value.
- **The variant is chosen by MessageFormat 2's preference:** among the variants whose every key matches, a literal key comes before `*`, and a number's exact key before its category, selector by selector, and then the order written.
- **A selection must be exhaustive, or it is a compile error:**
  - every plural selector, and every number selector but an exact one, covers every CLDR category of its locale, or has `*`, and every combination is covered when there are several;
  - an exact number selector has `*`, for the numbers its keys do not list;
  - a key that is not a category of the locale (`few` in `en`) is an error, because it can never be chosen.

  An uncovered count would otherwise render the key's name. Both reference catalogs already meet this rule.
- **A select on an input without `*`** (`month=1` … `month=12`) is closed by its type. A value outside it at run time throws a `GraiError` naming the key, the locale and the value.

## Formatting: numbers and dates

- **The options are Intl's, by name.** MessageFormat 2's number functions' options already are `Intl.NumberFormat`'s, and `:number` also takes `style` and the options that go with it, such as `style=percent` or `style=currency currency=EUR`. `:percent`, `:currency` and `:unit` are `Intl.NumberFormat`'s styles, and take the options MessageFormat 2 lists for each. `:currency`'s `fractionDigits` is both of Intl's fraction digits, and `auto` the currency's own; `:currency` needs `currency`, and `:unit` needs `unit`. `:unit`'s `usage` would convert the value into the units the locale prefers, which Intl cannot, so it is a compile error. MessageFormat 2's date and time functions are a draft whose options are still changing, so `:datetime`, `:date` and `:time` take `Intl.DateTimeFormat`'s options, such as `dateStyle=long`. Given no option that shapes the text, they use MessageFormat 2's defaults: a medium date, a short time.
- **`:relativetime` and `:list` format through `Intl.RelativeTimeFormat` and `Intl.ListFormat`,** made once like the others. `:relativetime` needs `unit` (`unit=day`), which Intl takes with each value, and its input is a `number`; `:list`'s is a `readonly string[]`.
  - **They take the bare names.** MessageFormat 2 defines neither, and asks that a function it does not define take a namespace, since a bare name may be defined later. But Paraglide already compiles `:relativetime unit=…`, so with the bare name its catalogs compile unchanged, and `:list` follows so that the functions read as one family. Both take Intl's options by name, as MessageFormat 2's own number and date functions do, so a definition it adds is likely to match; where it does not, grai follows the specification.
- **The options are checked when compiling,** by making the formatter once. An option a function does not take, or a value Intl refuses, is a compile error naming them.
- **Each locale and options gets one formatter, in `formats.js`, made the first time it formats.** Made at module scope, every locale's formatters would be made on every page load. A formatter made once formats a number in 207–213 ns and a date in 462–526 ns, against 8.3–9.3 µs and 21.7–23.9 µs for a new one per call (`intl`).
- **A formatted value is passed to Intl through `Number()`,** as Intl itself takes a date by its time value.
- **An option the app's data decides can come from an input: `currency=$code`, `unit=$unit` and `timeZone=$zone`.** Which currency an amount is in, which unit a quantity or a relative time is in, or which time zone a reader is in, is data. How the value looks, its style and its fields, is the message's to write, so those options stay literal and are checked when compiling.
  - The compile checks such a call with a value the option takes, so the literal options around it are still checked. A currency needs `style=currency` written beside it, and a unit `style=unit`, or Intl would leave them out. So a call takes one option from an input at most.
  - The input is typed `string`. A value Intl refuses throws a `GraiError` with the code `format-option-invalid`, which names the option and the value.
  - Each value gets its own formatter, made the first time it formats and kept in a map. A number formats in 216–305 ns with its currency from an input, against 205–248 ns with it written; Paraglide, which finds a formatter by the options each call builds, takes 688–1,054 ns (`option-inputs`).
  - `:relativetime`'s `unit=$unit` is the exception, as Paraglide takes it too: Intl takes a relative time's unit with each value, not when its formatter is made, so the call keeps one formatter and passes it the unit. The input is typed `Intl.RelativeTimeFormatUnit`, and a value that is not one throws the same `GraiError`.
- **A date's time zone is an input, not a value bound once per request as the locale is.** Bound per request, it costs a date the same, 450–556 ns against 447–601 ns from an input (`option-inputs`), so the choice comes down to where the zone is known. A server and a page agree on a date only if both read its zone from the same place. With an input, that place is the app's own data, which it already renders on the server and hydrates with. A zone bound per request would also have to reach the page, and every date without a zone would still differ between a server, which formats in its own zone (UTC on Workers), and a browser, which formats in the reader's.

## Errors

- **Every failure is a `GraiError`** with a `code`, the `file`, and the `key` and `locale` where they apply. Its message says what is wrong and what to do: for example, `messages/pl.json: "cart_items" (pl): no variant matches countPlural=many. Add one, or a variant with * for the selectors it does not care about.`
- **A compile reports every error at once, sorted by file, key and locale, and exits non-zero.** It leaves the last good output in place, and the Vite plugin shows the errors in the overlay while the last good output keeps serving.
- **Anything grai needs that it cannot read or parse is an error that names it:**
  - the config file, a field of it, a configured locale's catalog, or a catalog that is not JSON;
  - a catalog with no messages, which is an error for its locale.

  A compile never succeeds with fewer locales or messages than configured, and each of these cases has a test.

## Incremental compiles and atomic output

- **A compile reads the catalogs as bytes and hashes them first.** When the manifest says the output was compiled from the same config and bytes by the same compiler, and every file it lists is there, the compile stops: nothing is parsed and no file is touched. "The same compiler" is a hash of the modules a compile and its saved build load, with the runtime and the templates the output copies, taken once a process, because the version alone would miss a local build of grai, or a patched install. The rest of the package, its adapters and its CLI, is no part of it: reading all of it cost a dev server's start about 8 ms, against about 3 ms.
  - **The modules are found by parsing them with oxc, following every import of a value, an import for its effects alone and an `import()` of a literal path,** so no way of writing an import hides a module. A path no literal gives, or one that is none of grai's files, makes the hash every module of grai's, as no list of them is then sure.
- **A recompile after an edit redoes only what the edit changed.** It keeps the last build in memory: each catalog's bytes and parse, each key's compiled code, each shard's text.
  - A catalog whose bytes are the same is not parsed again.
  - An edited catalog laid out one entry per line, as editors and formatters write them, has a line break and the same indent before each top-level key and nowhere else, because a JSON string holds no raw line break. The edit's changed bytes lie between two such entry starts, so only that span is parsed, in the old file and in the new. The span must be whole entries with their separators: a comma or the opening brace before it, and a comma after it unless it closes the object. Whenever that cannot be shown exactly (another layout, a duplicated key, a span that does not parse, a separator missing or one too many), the whole file is parsed instead, and reports what is wrong.
  - Only the keys whose messages changed are compiled, and only their shards are rendered and written.
  - A failed recompile leaves the last good build as it was, so the next one starts from it.
- **A watcher starts from the build the last one saved.** A watcher saves its first build in `.grai/build`, as V8 serializes it, once the process is quiet (half a second in which its event loop worked less than a tenth of the time), when the watcher closes, or as the process exits. A start keeps the loop busy, so the save, about 20 ms for app A, never lands in one: a fixed second did, in the middle of app A's 5 s start. The save at exit, written synchronously, covers a server stopped before it was quiet: Vite closes its server on SIGTERM, but in an app whose own SIGTERM handler exits at once, the server never closes. The next watcher's first compile starts from it as a recompile starts from the last build: a catalog changed in between is compiled as an edit, and each file is compared with the outdir's, which another compile may have written since. A cold dev start then compiles only what changed since the last one, in place of every key.
  - It is taken up only when the same grai saved it, on the same V8 and ICU, from the same config, with the same options (the pseudo-locale, the locale copies): anything else and the compile starts from nothing.
  - The save is written whole and renamed into place, so a watcher reads one process's build or another's, never part of one, and any of them is a sound start. Each save writes a file of its own, which it creates, `build.<pid>.<uuid>.saving`: two watchers of one outdir in one process once saved through one file at once, and the build renamed into place, part of each, read whole and rendered old words. The file says how long the build is, so one a crash cut short is not taken up either. It takes no lock, which would hold up an edit's compile while it writes: it writes to a file of its own, which is no temporary file to a compile under the lock, so a compile never removes a save under way; the next save removes one a crashed process left.
  - It costs disk: 22 MB for app A (6,379 keys × 3).
- **Watching covers the config and the catalog files, nothing else.** No other file can start a compile, so a framework's generated files never trigger one.
  - Each file is watched as a file, not through its directory, whose events macOS reports late.
  - The watches are set up again before each compile, so a file an editor saves by renaming another over it is seen, and so is a change during the compile.
  - A catalog that does not exist yet is watched for through its directory.
- **Each file is written to a temporary file of the writer's own in `.grai/` and renamed into place**, which is atomic on POSIX file systems. A reader sees the old file or the new one, never part of one. The texts go to their temporary files all at once; then the files named by their content are renamed into place, then the entries.
- **A compile publishes the output whole, and a reader sees one compile's output, never two mixed.** Whole files are not enough. When an edit changes a formatter's options, `formats.js` and a shard change together, and a reader that loads between the two renames gets the new `formats.js` beside the old shard, which imports a formatter it no longer exports. No order of the writes avoids it: the opposite order fails the opposite way. Nor does a `formats.js` that keeps both formatters until the shards are written, since a reader whose load spans the compile still reads one shard before and the other after, and a doubling of the shard count, which moves keys from shard to shard, has no such order at all.
  - **Every file that only the output imports is named by a hash of its content** (`keys/3-1f0c2b7a9e4d.js`, `formats-….js`, `runtime-….js`), so it is written once and never replaced. A shard's module and declarations share their name, so TypeScript reads the declarations and not the module, as it does for any `.js` beside its `.d.ts`.
  - **The entries keep their names:** `messages.js`, `keys.js`, `runtime.js`, `server.js`, `testing.js` and `internal.js`, with their declarations, which apps, package.json `imports` and adapters name. `keys.js` imports its compile's shards by their names, and is renamed into place once they are all there. A module loader reads a module before the modules it imports, so whichever `keys.js` it read, every shard it then reads is of that compile.
  - **Content that does not change keeps its name,** so an edit writes one shard under its new name, its map, and the two entries that name it, `keys.js` and `keys.d.ts`, and every other file stays as it is, with file watchers', Vite's and TypeScript's state of it. A compile also skips any file that the last one left in place, which makes undoing an edit cost no more than the edit.
  - **A file the output no longer names stays for ten seconds,** for a reader that read an entry of the compile before and has the rest still to load, and the next compile after that removes it. A module loader takes milliseconds to read an output.
  - **The outdir is the output's alone, and a compile owns all of it.** A file the manifest does not record, which an earlier layout of the output or a compile that stopped halfway left, is no compile's whose entries a reader can hold, so the next compile removes it at once, and a temporary file in `.grai/` too, since only a writer under the lock makes one. An outdir that holds files but no `.grai/` is no compile's: grai refuses it (`outdir-not-empty`) rather than remove someone's files, as the config refuses one that holds the config or a catalog.
  - **A declaration map is named by its shard's index, `keys/<n>.d.ts.map`, and replaced in place.** TypeScript follows a map only when the map names its declarations, so a shard's is written again with the shard. A key added near the top of the base catalog moves the lines of every key after it, in every shard: the maps are then written again, and no shard is renamed, which would have TypeScript read every declaration again. Only go to definition reads a map, after its declarations.
  - **A shard names the modules it imports, so a new one renames every shard that imports it.** The formatters' module changes only when a message adds or drops a formatter's options: neither app A's catalogs nor app B's format a value yet. The runtime a shard reaches through the anchor, which keeps its name.
- **What is in the outdir is learned from the outdir.** The manifest names each file of the output, with a hash of what each entry and map holds, and a compile writes a file that is missing from a listing of its directory, or whose hash the manifest does not record. Nothing is taken from the last compile's memory of what it wrote, which another writer or a file deleted by hand makes wrong. A compile that replaces a file removes the manifest first and writes it last, so one that stops halfway leaves no manifest to trust.
- **A process holds one runtime, through one anchor.** An application imports several entries, and a process reads each at its own moment: one that pinned the runtime by its name would take, across a change of config, the middleware's runtime of one compile and the messages' of the next, two runtimes that each bind their own locale. So every entry and module of the output reaches the runtime and the config through `internal.js`, the one module whose text a change of config or of grai rewrites, and the runtime is the one module that imports the config. A process reads the anchor once, so its middleware, its messages and its adapters share one runtime, whichever compile's it read.
  - **The entries but `keys.js` then change only with grai,** never with the config: `runtime.js` lists the API from the anchor, and `server.js` and `testing.js` import the anchor. A change of config rewrites the anchor alone, and no shard, since no shard names the runtime's module.
  - **A shard checks the locales it was compiled for against the runtime's,** at their positions, as it loads (`assertCompiledFor`): a message picks its locale's function by that position. The keys and the anchor are read at two moments too, so a change of the locales while a process loads the output can pair the keys of one compile with the runtime of another, and the process then fails with `output-changed`, saying to load the output again, rather than render one locale's words for another. Any other change of config leaves the keys as they were.
  - **The Vite plugin reloads its pages and its servers' modules, the anchor among them, after the anchor changes,** so a page that loaded one runtime never takes a second.
- **The other designs, weighed and set aside:**
  - **A directory per compile, swapped in by one rename of a symlink.** Node, Vite and TypeScript resolve a symlink to the real path, so a reader stays in the compile it started in. But every edit then moves every file to a new path: TypeScript reads every declaration again, and Vite takes every module for a new one, so an open page that imports one more module loads a second runtime.
  - **A versioned import map**, which the entries would resolve through. Node and TypeScript read no import map, and the package.json `imports` an app maps its keys with are read once per process.
- **One writer per outdir.** The writer takes a lock: a file holding its pid and its claim's id, linked into place from its process's claim, a file of its own made once (`lock.<pid>.<uuid>`), so that the lock never exists empty and no two writers share a claim, two threads of a process among them. A process's compiles take the lock in turn, a live writer's lock is waited for, 30 s at most, after which the compile fails and names the file to delete, and making a claim removes the claims of processes no longer running. The CLI's `watch` and the Vite plugin can then share an outdir.
  - **A lock whose writer is gone, as one killed while it wrote, is taken over, by one writer at a time.** Writers that each found the lock stale and removed it could otherwise both take it, the later removing the lock the earlier had just taken. So a writer first links its own claim to `lock.taking.<the dead writer's claim id>`, which one writer can and the others find taken, and removes the lock only while it still holds that id: no other writer removes it meanwhile, so the one removed is the dead writer's. A takeover whose writer died in turn is removed the same way first, and a live one is waited for as a live writer's lock is: a writer stopped in the middle of a takeover, as one paused by a debugger, holds the others no longer than its lock would. A lock is held only while a compile writes, so a dev server killed then leaves one, and the next compile, a build's, takes it over rather than stop.
- **In dev, the Vite plugin serves from memory and sends HMR itself.** It watches the config and the catalogs with `fs.watch` (3–10 ms to see a save, against 48–114 ms for Vite's watcher: `hmr`) and ignores every other file, and the output directory's changes are its own, so a compile is never reported twice. The plugin still writes the files, for TypeScript and editors.
- **An edit patches the page in place.** The dev module keeps every key's locales in a table. After an edit the plugin sends only the changed keys' functions, as a module the page imports; the page writes them into the table and dispatches a cancelable `grai:change` event on `window`. A framework adapter that renders again cancels it; otherwise the page reloads. The event's `detail.keys` are the edited keys, and each dev call first names its key to `globalThis[Symbol.for("grai.read")]`, which the adapter may set, so the adapter draws again only what read an edited key. The server's dev render takes the same patch, so an edit never evaluates the app again. A key added or removed, a key turned from text into markup or back, whose export a patch cannot give its parts or take them away, or a new runtime (a change of the config it reads, or of grai), reloads the page, and the server's environments take the module again. An edit that renames the plural rules or the formatters is still a patch: the patch imports them by their new names, and the rows it leaves keep the modules they were made with. It is 10–15 ms from the save to the page and 8.7–11.5 ms to a server render, against 225–251 ms for re-sending the whole module (`hmr`).
  - **A module that missed a patch asks for it.** Each patch has a number, and the dev module the count it was served with. A page or a server's runner may take the module before an edit and evaluate it after the edit's patch was sent, when the module had no handler for it yet: as it is evaluated, it asks for the patches made since its count, and writes them as it writes any other. A server's program then stays as it was evaluated, where reloading the module would evaluate it again.
- **A framework whose pages the server draws has the plugin reload them instead** (`reloadOnEdit`, for an adapter such as Astro's). An Astro page with no island loads no module of messages, so nothing on it could take a patch, and the words outside its islands are the server's anyway. The servers are sent their patch first, so it is under way before a reloaded page asks for a render; as on the in-place path, nothing waits for it to land.

## Runtime

The locale is resolved once per request on the server, or once per page on the client. A message call reads that bound value and never runs a strategy.

- **On the server, `server.js`'s middleware resolves the locale and binds it** to the request through `AsyncLocalStorage`. Its strategies:
  - `cookie`;
  - `preferredLanguage` (`Accept-Language`): its ranges by weight, as RFC 9110 reads them. A malformed range or weight (`q=2`, `de_DE`) is left out, and `q` is read in any case. `q=0` refuses every locale its range names (`en;q=0` refuses `en` and `en-GB`), and `*` takes any locale no other range names, the base locale first. A range reaches a locale as itself, then as each parent it is cut down to, as written and then in its likely form from CLDR (`zh-Hant-TW`, `zh-Hant`, `zh`; `zh-TW` is `zh-Hant-TW`), and never as a sibling: `en-AU` reaches `en`, not `en-GB` or `en-US`, which a config's order would otherwise choose between. A site that wants `en-AU` to read `en-GB` lists `en-AU` with a fallback to `en-GB`;
  - `query`: the URL's query parameter `queryParameter`, matched as a preferred language is, since a link may name `de-AT` where the project has `de`;
  - `url`: a non-base locale is the first path segment, and the base locale has no prefix. A locale's home page is `/de`, not `/de/`, which SvelteKit and Next would redirect to drop the slash; every other path keeps the slash the app wrote;
  - `localStorage` is the page's alone; the middleware passes over it to the next place.

  The base locale is always the last resort, so the config does not list it. `url` comes last unless every locale's paths are prefixed: every path names a locale, the base locale's when it has no prefix, so the config rejects a strategy after it, which would never be read. A page no server draws reads the same strategy (above).
- **With `"localePrefix": "always"`, every locale's paths have a prefix, the base locale's too,** so a path without one names no locale. The strategies after `url` then find the request's locale, which is the usual "the URL's locale, else the cookie's, else `Accept-Language`". The middleware sends a GET or a HEAD for such a path to that locale's path, with a 307: it keeps the method, and no cache keeps it for good, as the locale it found is the request's. Any other request is answered in that locale where it is, as a form's POST must not be sent elsewhere. `"as-needed"`, the default, leaves the base locale's paths unprefixed, as most sites have them.
- **`localePrefixes` gives a locale a prefix of its own** (`{ "en-US": "us" }`), one lowercase path segment that no other locale has, so its paths are `/us/…`. Without one, a locale's prefix is its tag.
- **`unlocalizedPaths` names the paths `url` leaves alone,** as globs (`["/app/**"]`): an app's pages kept by cookie beside public pages localized by URL, or an API that must not be sent elsewhere. Such a path has no prefix and names no locale, so the strategies after `url` find its locale, the middleware sends it nowhere, and `localizeHref` gives it back as it is. The globs are compiled into `config.js` as regular expressions, so a request tests them without parsing them.
- **`pathnames` gives a route its path in each locale's words** (`{ "/about": { "de": "/ueber-uns" }, "/products/[id]": { "de": "/produkte/[id]" } }`), for search engines and readers of the address bar. `localizeHref` writes a route in the locale's words, and `deLocalizeUrl` reads them back as the route, so what routes through it serves `/de/ueber-uns` from `/about`: a SvelteKit `reroute`, Next's proxy, and Astro's middleware, which renders the route at the words on demand. @xyrolle/grai/nuxt routes each page's copies at its locale's words instead, as Nuxt routes by its pages. A named segment (`[id]`) is carried across, and so is a trailing slash, as Astro links a page it writes into a folder, and each locale's paths must name the same segments, so no translation can lose one. Each path is kept percent-encoded, as a request's path arrives, and two routes may not share one locale's path. The table is in `config.js` only for a config that has pathnames.
- **`basePath` is the path the app is served under (`/shop`), and the locale's prefix follows it:** `/shop/de/about`. grai's config names it, as the output must be the same whichever tool compiles it, `grai watch` or a framework's build, and each adapter refuses a framework that serves the app under another: @xyrolle/grai/vite Vite's `base`, @xyrolle/grai/sveltekit/vite SvelteKit's `paths.base`, `withGrai` Next's `basePath`, @xyrolle/grai/astro Astro's `base`, and @xyrolle/grai/nuxt Nuxt's `app.baseURL`. The URL helpers keep the base path on a path that has it, as a browser writes it, and take a path without it as the app's own, as Next's `Link` writes it before adding the base itself, so `localizeHref` fits both. `localizeHref` reads a relative href from the page's URL, on the server the request's, as a link resolves it, so SvelteKit's `resolve()`, which writes a relative path as the server renders, needs no setting either.
- **`domains` gives each locale a host of its own** (`{ "en": "example.com", "de": "example.de" }`). On those hosts a request's host names its locale, before any prefix, and a locale's paths have none. A link to a locale on another host is a whole URL, so the middleware binds the request's origin beside its locale, and a page reads its own. Every locale must have a host, each its own: a locale without one would have no address that a link from another's host could name. On any other host, such as `localhost` in development, the URL is read by its prefix as without domains, so every locale is reached without the production hosts. @xyrolle/grai/astro holds Astro's `i18n.domains` to the same hosts.
- **Each of these options is a constant in `config.js`** (`prefixesEveryLocale`, `customPrefixes`, `leavesPathsAlone`, `translatesPaths`, `servedUnderBase`, `hostsLocales`), checked where the runtime would run that option's code. A bundler folds such a constant across modules and drops the code it guards, so a page pays only for the options its config names: the URL helpers a page calls are 578 B brotli with none of them, and 611, 613, 816, 649 and 675 B with `localePrefixes`, `unlocalizedPaths`, `pathnames`, `basePath` or `domains` (`bench/url-bytes.mjs`). Checking each option's value when the runtime runs instead would carry every option's code on every page.
- **A strategy the server defines is named in `strategy`, `custom-` and a lowercase name (`custom-session`), and defined in code** with `defineServerStrategy(name, { getLocale, vary })` from the output's `server.js`, as a function cannot live in a JSON config. The middleware asks it for a request's locale in the strategy's order, awaiting it, and goes on where it names none, so an app can read a signed-in user's choice beside grai's own places. Its locale must be one of the project's. A strategy the config lists but the server never defines fails the request that reaches it, and a definition the config does not list is refused, so neither can drift silently. `vary` names the request headers it reads; without it the response varies by every header (`Vary: *`), as nothing else says what it read. A page does not read it, and `setLocale` cannot write where it reads, so a page whose strategy keeps the choice nowhere else refuses `setLocale`.
- **The middleware's response lists in `Vary` the request headers its strategy reads:** `Cookie` for `cookie`, `Accept-Language` for `preferredLanguage`, and none for `query` and `url`, which read the URL a cache keys on already, or for `localStorage`, which a request does not carry. A shared cache then keeps a copy per locale, not one locale's page for every reader. They are appended to the handler's own `Vary` without reading it first, which would cost every request a header read: a header listed twice means the same to a cache. A response from `fetch()` has immutable headers, and no platform can say so in advance, so such a response is copied.
- **A call reads the bound locale once and indexes its variant with it:** the request keeps the locale's position in `locales`, so there is no search and no strategy per call. `setLocale` in a request changes the locale for the rest of that request, and for no other: it writes the state the middleware binds for the request, as Workers have no `AsyncLocalStorage.enterWith` to bind a new one.
- **Where no middleware binds requests** (scripts, crons, Node tests), one process-wide value is bound. It starts as the base locale, and `setLocale(locale, { reload: false })` changes it.
- **On a server, a call outside every request the middleware binds throws `locale-unbound`,** unless it names its locale. There is no reader's locale there, and the process's would render some readers' pages in another language. That's where a stream's `pull()` runs once the middleware has returned, since its reader starts it, so a body that renders in its pull fails instead of switching language after its first chunk.
  - Bodies streamed as frameworks stream them keep the locale in Node, Bun, Deno and workerd, and the tests pin them: a `start()` that pushes after awaits, as SvelteKit's does, and a task the handler started writing to the stream. React's renderer, which Next.js streams through, renders in work it schedules from inside the handler, and its `pull()` only flushes.
  - Not adopted: keeping the request bound while every body is read, through a stream of the middleware's own that reads each chunk inside the request, or through a `TransformStream` piped from there. Either costs every response with a body 0.9–2.1 or 6.6–9.3 µs in Node, and 20–27 or 29–35 µs in workerd, where a JavaScript-backed stream is what a response body costs most as. grai's whole middleware is about 2 µs there, and Paraglide's 7–10 µs.
- **On the client,** the page's `<html lang>` is the locale, which the server or the page's locale script writes, else the base locale. `setLocale(locale)` keeps the locale in each place the strategy lists, its cookie, `localStorage`, query parameter or path, and reloads, or goes to the URL that names it, unless the locale is the page's already: a picker that chooses its current value, or a preference written again at start, keeps the page and its state. With `{ reload: false }` it only keeps it, for the page's next load (`"reload"`, above).
- **The cookie's policy is four options, named as Paraglide names them** (`cookieName`, `cookieMaxAge`, `cookieDomain`, `cookieSameSite`), each for a case an app meets: subdomains that share a preference, and a page embedded in another site's. `setLocale` writes the cookie Secure on https, as a browser drops a Secure cookie an http page sets. It is Secure always where the browser requires it: `SameSite=None`, and a `__Secure-` or `__Host-` name. A `__Host-` name with a domain is refused, as a browser would drop the cookie. There is no option to write it insecure on https, which nothing needs.

The runtime's names are the ones existing Paraglide call sites use, so migrating changes imports, not calls. Only the middleware has a name of its own:
- `runtime.js`: `getLocale`, `setLocale`, `locales`, `baseLocale`, `Locale`, `isLocale`, `assertIsLocale`, `getTextDirection`, `MessagePart`;
- for the `url` strategy: `localizeHref`, `localizeUrl`, `deLocalizeUrl`, `extractLocaleFromUrl`. Without it they leave every URL as it is, since no URL then names a locale: in an app that keeps the locale in a cookie, `/de/…` is a path of its own, and a prefix would lead to a page it does not have;
- `server.js`: `middleware(request, ({ request, locale }) => response)`.

**`runtime.js` exports only that API.** It re-exports it from `internal.js`, the anchor of `runtime-<hash>.js`, the runtime's module, which also holds what the output's own modules call: the dispatcher the shards call, the request binding `server.js` sets, and what they read of the config. Those modules import the anchor too, and an adapter that binds the locale takes the binding from it. An editor then offers an app nothing it should not call. A bundle drops a re-export, so a page holds the same code as when one module gave it all.

**A page's or a script's test binds its locale with `testing.js`'s `useLocale`, which the output carries; a server's runs in `server.js`'s `withLocale`.** A server renders every message in a request, so a test, or a job such as a scheduled email, binds its locale as a request does, through the store the middleware binds, with `AsyncLocalStorage.run`: under Vitest, `aroundEach((test) => withLocale(locale, test))` runs the test inside it, its synchronous code and every continuation. A flag letting `useLocale`'s binding hold on a server would be a path only tests take, and `enterWith`, which binds without a callback, is experimental in Node and missing in workerd. It binds the locale that the runtime's module holds, which no module of the package can reach, and it takes the project's `Locale`. A component test can then render in any locale, since a test holds every locale's messages. A page keeps its rule, one locale at a time, so a test still fails where a production page would. `@xyrolle/grai/vite` refuses the module in a build, so it never ships.

## Servers

- **One middleware serves every runtime, with no adapter.** It takes a `Request` and a handler and gives back the handler's `Response`: the shape of a fetch handler on Workers, Bun and Deno, and of Hono's middleware in one line, `(c, next) => middleware(c.req.raw, () => next().then(() => c.res))`. An adapter would add a name and no behaviour.
- **On Workers it needs only `AsyncLocalStorage`.** Workers have it by default from compatibility date 2026-08-04, with the rest of Node.js compatibility. On an earlier date the `nodejs_als` flag adds it alone, and without it the Worker does not start: `No such module "node:async_hooks"`. `test/workers.test.ts` runs the example under the default, and its interleaving Worker with `nodejs_als` alone.
- **A request's locale holds across its awaits in workerd, Bun and Deno, as in Node.** In the test, 30 requests in three locales go through the middleware at once in each runtime, and each renders again after an await, once all 30 have rendered, in its own locale or in the one its `setLocale` chose. They interleave inside one HTTP request, as no request may wait on another: workerd cancels a request that has nothing of its own left to run, as hung, and Bun closes one that has waited 10 seconds, so 30 requests that each waited for the rest failed now and then under load.
- **The tests get Bun and Deno from pnpm's runtime protocol** (`"bun": "runtime:1.4.4"` in the devDependencies), as they get workerd from Wrangler: one `pnpm install` brings every runtime they serve the example in, at a pinned version, with nothing installed globally.
- **A framework that renders apart from any handler the middleware could wrap takes its parts:** `localeOf`, the locale it binds, `redirectOf`, the redirect it answers a page asked for without the prefix it needs, and `vary`, the headers it adds to `Vary`. They are the middleware's own functions, so the two cannot drift; `@xyrolle/grai/nuxt` binds Nuxt's render with them.

## SvelteKit

- **`handleLocale({ middleware, getTextDirection, localeCopies })` is the whole server adapter.** It takes them from the project's output, as every adapter takes the project's generated modules, and runs the middleware around Kit's `resolve`. The locale is resolved and bound once, for the page's render and its loads alike.
- **The page's locale and direction are written into `src/app.html` through `%grai.lang%` and `%grai.dir%`,** by `transformPageChunk`. They are placeholders, as Paraglide's `%paraglide.lang%` is, so migrating renames them, and the app keeps its `<html>` as it wrote it.
- **The browser needs nothing from the adapter.** The runtime takes `<html lang>` as the page's locale.
- **`reroute` is one line in the app,** `deLocalizeUrl(url).pathname`, and not an export: wrapping the output's own helper would add a name and no behaviour.
- **A navigation to another locale's page loads it as a document.** A page holds one locale's words, and its `<html lang>`, runtime locale and import map belong to the document, so Kit's client would draw such a page with the first page's locale. `reloadAcrossLocales` in the root layout runs on Kit's `beforeNavigate`: when putting the target in the page's locale (`localizeUrl`) changes its path, the target is another locale's, and it cancels Kit's navigation and loads the URL; back and forward, which have moved the browser already, reload it. A navigation within the locale, under a strategy that reads no URL, or to a path the `url` strategy leaves alone, stays Kit's. It reads the locale through the runtime's public `localizeUrl`, so the rule is the URL helpers' own.
  - It is Kit's own hook, so links, `goto` and history are all covered, where `data-sveltekit-reload` on each link would miss `goto` and history, and a click handler would miss both.
  - Returning a path no route matches from `reroute`, which Kit loads as a document, would need no layout, but an app with a catch-all route would draw the other locale's page in the client after all.
  - Switching the page's chunks to the other locale's in place is `"switch": "live"`, not built yet.
- **A built page downloads only its locale's message chunks.** `handleLocale` writes one import map entry, from the build's `chunks/grai/` to `chunks/grai-<locale>/`, ahead of Kit's preloads, so every message chunk the page and its later navigations import is the locale's copy. It also rewrites Kit's `modulepreload` links to the shared chunks to name the copies, as browsers apply no import map to `modulepreload` and would fetch both (`bench/preload.mjs`).
  - It finds the build's directory from Kit's preload of its client entry, `…/immutable/entry/start.*.js`, resolved against the page's URL, so it follows the paths Kit itself writes, and takes no option.
  - A page without that preload (no client JavaScript, or dev) is left as it is.
  - Under a `csp` whose scripts need a nonce, the import map carries the nonce of Kit's own inline script, as Kit writes no placeholder for it outside `src/app.html`. Under hashes the browser refuses the map (`docs/followups.md`).
- **The copies come from `@xyrolle/grai/sveltekit/vite`'s plugin,** which is `@xyrolle/grai/svelte`'s with `localeChunks` on: the SvelteKit adapter asks for them, and an app without it ships none. Its compile writes `localeCopies = true` into the output's `config.js`, which `server.js` exports and the app passes to `handleLocale`, as it passes the output's functions; every other compile writes `false`. `handleLocale` writes the map only when it is true, so a page never names copies its build did not write; built with `@xyrolle/grai/svelte`'s plugin, a page loads the shared chunks and every locale's words. The flag travels in the output, not as a define into grai's own code, so grai stays outside the app's server bundle, with one instance of its request state. The copies are the config's to decide, before either build runs, so it holds whichever Kit builds first.
- **In dev, `@xyrolle/grai/sveltekit/client` draws an edit again in place.** It gives each key Svelte readers, made with `createSubscriber`: the read hook subscribes the render that calls a message, and an edit reruns the renders that read an edited key, and nothing else. Once the server has the edit, it also calls Kit's `refreshAll()`, so the page's loads and remote functions run again for the text they return. A server's runner sends `grai:patched` when it has written the patch, and the plugin passes it on to the page: the loads never run again on a server still without the edit, and a page whose text all comes from its loads, which holds no module of messages to dispatch `grai:change`, still hears of it. Text a component works out once in its script, outside its markup and `$derived`, shows the edit when the component mounts again.
  - `createSubscriber` keeps it a plain module, which the package builds as it builds the rest. A `$state` per key would skip the render effect `createSubscriber` makes for each call, but needs a `.svelte.js` module that the app's Svelte compiles; this runs in dev only.
  - Svelte's own hot update would mount again every component that imports the messages, which is all of them, and lose their state.
  - It is one import in `src/hooks.client.ts`, which a build leaves out, as `dev` is false there.

## Vue

- **A message is a plain function, so calling one in Vue needs nothing from an adapter.** A template calls a function `<script setup>` imports. A `$t`, a global property or an injection would cost a lookup per call and hide the key from the bundler.
- **A Vue app imports the messages as a namespace, `import * as m from "…/keys.js"`.** Vue's compiler takes a named import such as `import { m }` as a value that may be a ref, so the template reads it through `unref(m)`, the namespace escapes, and the bundler keeps every key of the catalog. A namespace import it takes as a constant, so the template calls `m.key()` itself and each chunk keeps the keys it calls (`test/vue.test.ts` pins both, so a Vue that changes either changes this advice).
- **A server render binds the locale through the output's middleware, around `renderToString`.** Vue renders a request's app within that one call, so the binding reaches every setup, render and await of it, as Kit's `handle` does. Interleaved renders in different locales keep their own (`test/vue.test.ts`). `@xyrolle/grai/vue` has nothing for the server, because the output's `middleware` is already the whole of it.
- **The browser's locale is the page's `<html lang>`,** which the server writes, so the page hydrates in the words it was drawn in.
- **`Markup` takes a map of functions, one per element, as `@xyrolle/grai/react`'s does, rather than named slots.** Vue's type checker takes every slot as optional and any slot name as valid, so slots could not make a missing or an extra element a type error. The map is typed by the tags of its parts (`MarkupElements<NoInfer<Tag>>`), which `MarkupMessage` names, so it must name exactly the elements the message writes. Each function gets what its element encloses, and the options and attributes the message writes on it (`{#link href=|/terms|}`). It is a functional component: it keeps no state, and costs no component instance.
- **In dev, an edit renders again in place, and the page keeps its state.** The dev module names each message call's key to `globalThis[Symbol.for("grai.read")]`, as for `@xyrolle/grai/sveltekit/client`, and `@xyrolle/grai/vue/client` makes that a read of the key's own `shallowRef`. On `grai:change` it changes the edited keys' refs instead of reloading, so the renders, computeds and watchers that called an edited message run again, and no other. It is behind `import.meta.hot`, which a build defines as undefined, so production ships nothing reactive under `"switch": "reload"`. A message called once in `setup` keeps its old words until the page loads again, as anything computed there would. `"live"` can make a Vue page re-render in the locale it switches to through the same read, once the runtime calls it and dispatches `grai:change` after a switch.
- **A page loads only its locale's words through @xyrolle/grai/vite's `localeChunks`, with nothing from `@xyrolle/grai/vue`.** The page's locale script keeps the `<html lang>` the server wrote, as it keeps a prerender's, and points the page at that locale's copies of the message chunks. `index.html` stays a valid page in the base locale, which the render writes the request's locale into, rather than a template of placeholders.

## Nuxt

- **A module, as Nuxt takes its integrations: `modules: ["@xyrolle/grai/nuxt"]`.** It compiles in its setup, before Nuxt builds anything, so the server's modules, `nuxt prepare` and `nuxt typecheck` find the output. A build fails on a compile error; dev goes on, and shows the next compile's errors in the overlay.
- **A server middleware resolves the locale once per request, and the app's plugin binds it for the render.** Nuxt renders apart from any handler the output's `middleware` could wrap, and bundles its server and its app apart, each with a copy of the output, so a binding in the server's copy cannot reach the app's. The server middleware resolves the locale with the output's `localeOf`, the middleware's own lookup, keeps the runtime's record of it (`{ index }`) on the request's event, which both are given, and adds the headers the strategy read to the response's `Vary`. The plugin has the app's runtime read it from the Nuxt app of the render (`tryUseNuxtApp`): every setup, template, plugin and route middleware of a render finds that app, and `<script setup>` finds it again after an await.
  - Interleaved requests keep their own locales, before and after a page's await (`test/nuxt-example.test.ts`).
  - A message rendered where no render can be found, at a module's top level or after an await outside a setup, throws a `GraiError` (`locale-unbound`) rather than render the base locale's words.
  - A `setLocale` in the render changes that record, so the rest of the render is in the new locale, and so is the page's `<html lang>`, which the head writes after the render.
- **`<html lang>` and `dir` are written through `useHead`,** so the page hydrates in the locale it was drawn in.
- **The url strategy routes each page under each locale's prefix but the base locale's, through copies of the pages in Nuxt's `pages:resolved` hook,** as @nuxtjs/i18n does. A copy is named `<name>___<locale>`, as @nuxtjs/i18n names its own. A route's locale is its prefix, so the middleware's strategy and the router always agree.
  - The copies follow the config's routing as the output does: each locale under its prefix from `localePrefixes`, the base locale too under `localePrefix: "always"`, and no copies of a page at a path `unlocalizedPaths` names. A page's path is a route pattern (`/docs/:page()`), which a glob matches as it would the paths it routes, but for a glob that names some of a parameter's values (`/docs/{a,b}`): that page is copied, and its left-alone paths still find their locale after `url`.
  - Under `"always"`, the server middleware sends a page asked for without a prefix to its locale's path, with the output's `redirectOf`, the middleware's own redirect.
  - Only paths are localized: a name leads to the base locale's page, and a link names its locale with `localizeHref`.
  - A link into another locale loads the page anew, through a global route middleware, since a page holds its own locale's words alone and a navigation in place would show the other locale's page with them.
  - `app.baseURL` must be `/`, since the strategy reads a path's first segment (`docs/followups.md`).
- **A page downloads only its locale's message chunks.** @xyrolle/grai/vite keeps them in Nuxt's `_nuxt/grai/`, and each locale's copies in `_nuxt/grai-<locale>/`, where Nitro serves them. The plugin adds one entry to the import map Nuxt already writes for its entry, and points the page's preload and prefetch links at the copies. It does so in unhead's `ssr:render` hook, on the head's tags, so no HTML is parsed. A page without Nuxt's import map is left as it is, with every locale's words.
- **@xyrolle/grai/vite runs in the browser's build only.** Nuxt runs its server's dev modules in vite-node, outside Vite's module runner, so @xyrolle/grai/vite's patch of a runner would not reach them. Nuxt invalidates those modules when grai writes the output's files, so the next server render has the edit, and the open page renders it again in place through `@xyrolle/grai/vue/client`, which the plugin imports.
- **`ssr: false` is refused,** since the server picks each page's locale.

## Reading code

grai reads an app's code to know which keys it reads: to report a key no catalog has, to remove a key nothing reads, to find and rename a key's reads, to migrate another library's calls, and to chunk a build's messages by the pages that read them. It reads code as the bundler does, everywhere, with one mechanism.

- **One reader, in `src/code/`, and nothing else reads code.** `check`, `check --fix`, `find`, `rename`, `migrate`, `@xyrolle/grai/svelte`'s text calls and the Vite plugin's key reads all take what it gives, so no two of them can read a file differently.
  - `parse.ts` is the only module that imports the parser. It gives a file's, or a piece of a file's, ESTree and module record, with offsets in the file's UTF-16, and its errors.
  - `components.ts` reads a Svelte, Vue, Astro or MDX file as its scripts and its template's expressions, each parsed by `parse.ts` at its place in the file. It also gives the scopes the template opens: `{#each … as item}`, `{#snippet row(item)}`, `{@const}`, `{:then value}`, `let:`, `v-for` and `v-slot`.
  - `scopes.ts` gives the declaration each name refers to, by ECMAScript's rules and TypeScript's (a type binds no value), with a component's template scopes inside its scripts'. It is the one scope reader, which `migrate` uses too.
  - `facts.ts` gives what a file imports and exports, and each use of each name it imports: a member read, an index, a destructuring, a call, a use whole, and each dynamic import. Its result is plain data about one file, which knows nothing of the others. That makes it a pure function of the file's text, so workers compute it and it is cached by content, on disk (below).
  - `modules.ts` resolves imports and follows a name through re-exports to grai's output. It takes the resolver as an argument: `oxc-resolver` for the CLI, the bundler's own resolution in a build.
  - `reads.ts` turns facts and module reach into the reads of the messages, with their places. These are what the commands and the build consume.

  ```ts
  // The CLI: every source under the roots, read and resolved.
  readSources(config, roots): Promise<Reading | ParseErrors>
  // A build: one module, by the bundler's resolution.
  readModule(path, text, resolve): Promise<ModuleReading | ParseErrors>
  type Reading = {
    reads: Read[];        // a key read, with its place and its file
    reaches: Reach[];     // computed reads, whole uses and loads by pattern: the keys each may reach, with its place
    tests: Read[];        // the reads of test files, which ship nothing
  };
  ```
- **The parser is `oxc-parser` (0.155 today), grai's first runtime dependency, with `oxc-resolver`.**
  - Install size: 4.7 MB for the parser on macOS arm64 (the package, 2.9 MB of it a WebAssembly build for platforms without a native one, and a 1.7 MB native binding). The resolver adds 1.6 MB.
  - It is the parser Vite 8's Rolldown is built on. It parses TypeScript and JSX, and gives ESTree with UTF-16 offsets, names with their escapes read (`title` is `title`), and errors with their places.
  - Parsing app B's 6,980 scripts (53 MB) to full ESTree takes 0.6 s through its raw transfer. The same parse returned as JSON takes 2.8 s.
  - The build uses grai's copy too, not Vite's re-export. With one version, the build and the CLI read every file into the same tree. A Next project, which has no Vite, reads code with the same parser. Loading a second copy of the parser in a Vite build costs one native binding.
  - The resolver is the one Rolldown resolves with, published for Node. It reads the project's tsconfig `paths` (with `extends`, so SvelteKit's generated `.svelte-kit/tsconfig.json` brings `$lib`) and package.json `imports` and `exports` under the bundler's conditions. It caches by directory: app B's 24,573 distinct imports resolve in 0.6 s cold.
    - The project's tsconfig applies to every module, as SvelteKit, Astro and Next apply its paths: to a component too, which the `include` of a tsconfig found by the file's own place may leave out.
    - A tsconfig the resolver cannot follow, such as one that extends what a framework generates before it is generated, or a Vite config that does not load, fails the command (`resolution-invalid`) with the fix. Otherwise every import would resolve to nothing, and the command would read nothing.
  - The CLI also reads the bundler's own aliases. When the project has a Vite config, Vite's own config loader, `loadConfigFromFile`, gives the aliases the config declares. Those aliases apply first, as Vite applies them: a string matches the whole path or a path below it, and a regular expression replaces what it matches. Then the resolver runs with the tsconfig and package.json rules above.
    - The loader runs none of the config's plugins, as SvelteKit's would sync its generated directory: a command that reads code writes nothing of the app's.
    - So a plugin's aliases come from the tsconfig the plugin generates, as SvelteKit's `$lib` does.
  - **The output's imports resolve only once it exists, so a command that reads code compiles it first when `messages.js` or `keys.js` is missing,** as the app's dev server or build would. The output is grai's alone.
  - Node's own resolution knows neither tsconfig paths nor TypeScript's extensions. TypeScript's module resolution needs `typescript` and is slower. Running Vite's resolver needs the app's Vite config loaded, which a Next project does not have.
- **A component is read through its framework's own parser, and its expressions through oxc.**
  - Svelte: `svelte/compiler`'s `parse` (the modern AST) gives the scripts and every expression's place.
  - Vue: `vue/compiler-sfc`'s `parse` gives the blocks and the template's expressions as text with their places, `v-for`'s parts among them.
  - Astro: `@astrojs/compiler-rs`, the parser Astro 7 itself depends on, loaded through the project's `astro`.
  - MDX: `@mdx-js/mdx`'s parser.

  Each expression's text is then parsed by `parse.ts` at its offset. Script and template therefore come out as one kind of tree: in TypeScript where the component's script is, and with JSX where the template allows it. Each framework is an optional peer, loaded only when the project has such a file. A component whose framework is not installed is an error that names the package. No markup is read as text.
- **A file that does not parse fails the command,** with the parser's message at its place, as the bundler fails it (`source-invalid`). It is never read another way. `check` and `find` report it, and `check --fix` and `rename` refuse to act, since the reads of a file they cannot parse are unknown. `migrate`, which changes each file alone, leaves that file and reports why.
- **Scopes are ECMAScript's, exactly.**
  - These declare names: `var`, which reaches the nearest function body or static block, `let`, `const`, `class` and `function` (hoisted). So do parameters, a caught error, imports, TypeScript's `enum`, `namespace` and `import x = require()`, and a template's blocks.
  - A type, an interface and `declare` bind no value.
  - A name reads the nearest declaration of it. A `const` set to the namespace (`const t = m`) is the namespace too, since it cannot change. Any other copy is a use of the namespace whole.
  - The "not checked: declares m again" path goes. Every read is placed exactly.
- **Module reach comes from the module graph, never from a name or a path.**
  - An import is grai's if it resolves to the output's `messages.js`, `keys.js` or a key's path, or to a module whose export of that name does, followed through re-exports. A module's exports are those the bundler runs: an export of a type, a `declare`, a type-only import or a namespace of types alone is erased with it, so an `export *` of the same name is what an importer gets. A key's path that the app maps to keys.js (`…/messages/<key>.js`) resolves to that key's own module, as the build resolves it; through keys.js, its namespace object would hold every key.
    - `export { m } from`, and an import exported again;
    - `export * as`;
    - `export *`, where a name a module exports itself wins over a star export of the same name, as the bundler binds it;
    - a default export.
  - An import that does not resolve names no file, so it names none of grai's. The one exception is a path that ends in the output's directory and one of its modules, which nothing the project declares resolves: no Vite alias, no tsconfig path, no package.json `imports`. That is an error naming the import and saying where to declare the alias. It is never taken for grai's or for not grai's.
  - `require()` of a literal path is an import, as the bundler converts it.
  - In a build, the bundler's resolution gives every import, and per-key paths resolve to its key modules (`\0grai:key/title`).
- **What a read reaches:**
  - **A key, read by name:** `m.key`, `m?.key`, `m["key"]` and a template without substitutions; `{ key }`, `{ "key": name }` or `{ ["key"]: name }` taken apart from `m`; a key's path imported statically or dynamically, destructured or not, read once, at the key's name in the path; and a named import of keys.js. Each use of the name such an import binds is that binding's reference, not a read of its own, and a `const` that holds a key's read (`const t = m.title`) reads it once, however often it is used.
  - **A computed read, `m[expr]`, reaches every key the index can be.**
    - A literal is the one key.
    - A template that starts with text, or text joined to something, reaches every key that starts with that text.
    - A choice between literals (`a ? "x" : "y"`) reaches those keys.
    - Anything else reaches every key.
  - **A use of `m` whole** reaches every key: passed on, spread, `Object.keys(m)`, `for…in`, a rest taken apart, or a copy that is not a `const`. So does a namespace import of keys.js used whole. A module's namespace object used whole, or read by a computed name, reaches the keys its exports hold, and an app module that exports none of grai's reaches none.
  - **A dynamic import with a literal path** is the import it names: a key's path reads that key, and messages.js or keys.js is the namespace, read through what the code does with it.
  - **A dynamic import with a template path** reaches the keys whose path the template matches, `${…}` standing for any text without `/`. This is how Vite's dynamic-import variables expand one into a glob. **`import.meta.glob`** reaches the keys its pattern matches.
  - **A dynamic import of anything else (`import(path)`) reaches nothing,** as the bundler treats it: it bundles no module for it, and the import is left to the runtime.
    - In a Vite build, a key's path resolves to a module that exists only in the build, so no runtime import can reach it.
    - The gap: an app that imports the output unbundled (Node or a test running `keys.js` as written) can load a key's module by a path it builds at run time. That load is outside what any build tool sees, and the guide says so (`docs/guide.md`).
    - So for `check` it is no read, and for `check --fix` a key only such an import loads is unused. For `rename` it is nothing to refuse.
  - **A type that names a key** (`typeof m.key`, an import type of a key's path) is a read for `check`, `check --fix`, `find` and `rename`, since removing or renaming the key would break the type. It is not a read for chunking: no runtime code reads it.
  - **JSX text, regular expressions against division, comments, strings and escapes are the parser's,** and stop being questions.
- **What the commands do with the reads:**
  - `check` reports each key read that no catalog has, at its place. A key is unused when no read of shipped code reaches it.
  - A computed read or a whole use that keeps keys no read names is listed with its place, as `check --fix` lists it. A key only tests read is unused, and the report names those tests.
  - `check --fix` removes the unused keys and lists each one it removes, so nothing is deleted silently. The check after it takes the reading the fix made.
  - `find` lists every read of the key: by name, with each use of a name such a read binds, and the computed reads, whole uses and loads that may reach it.
  - `rename` edits exactly the spans of the key's reads by name. That covers a member, a string or template, a path's last segment, an import's or a re-export's name, and a binding named after the key (a per-key import's, a shorthand pattern's), with every reference to it. An escaped name, in an identifier, a string or a path, is written plainly.
    - A reference written in shorthand is written out in full: `{ title }` becomes `title: heading`, Svelte's `{title}` and `bind:title` become `title={heading}` and `bind:title={heading}`, Vue's `:title` becomes `:title="heading"`. The template readers record each shorthand with its place, as only they see that a name stands for an attribute too.
    - A name the key keeps through modules is renamed in each of them: a re-export by the key's own name, and every import of it by that name, as the key's name is the module's export then. A name a module gives the key (`export { title as heading }`) is that module's, so it and its importers stay.
  - `rename` refuses only for these reasons, each named with its place:
    - a computed read, whole use or pattern load that may reach the key;
    - a binding it would rename that would collide with, or capture, another name in its scope;
    - a new name another key has.

    It no longer refuses for mentions, escapes, JSX text, `/` or a namespace declared again.
  - **A build reads each module through Vite's pipeline, at grai's own transform with `enforce: "pre"`, with the same reader and the bundler resolving.** It sees what the user wrote, plus what an earlier pre plugin added, such as an auto-imported `m`, and a virtual module's code. It sees a component before it compiles, so `components.ts` reads a `.vue`, `.svelte` or `.astro` file there exactly as the CLI does. Vue's compiled template would read a script's import through `unref(m)`, a use whole.
    - So a build and `check` find the same reads at the same places, with two exceptions, both from what only the bundler has. One is a virtual module, which the CLI cannot see. The other is code that an earlier pre plugin injects, which `check` reads only if the injecting plugin's output is a file.
    - Chunking links modules by what the bundler ships, the module's transformed code read by the same parser, since only that shows Vite's expanded globs.
  - `migrate` parses and scopes through the reader. It finds a component's imports of the library from the component's parse, not from its text, so a comment or a string that spells one is none.
- **Performance is measured against main in one window, and earned back without losing exactness:**
  - The commands measured are `check`, `check --fix`, `find` and `rename` on the synthetic project and app B (the refactor bench), together with the build's check and `test:performance`.
  - **A command parses and resolves only the sources whose text may name grai's output** (`code/candidates.ts`). Every other source reads nothing of grai's.
    - A file reads the messages only through an import, a load or a glob that names the output or a module that passes it on. So its text must write one of these:
      - the output directory's name, or a barrel's name: its file's, its folder's too for an index, or that of a folder above it whose package.json may name it as its entry. A path whose last segment is `.` or `..` names a folder without its name, so it counts too;
      - the key of a mapping that may name one without that name: a Vite alias, a tsconfig `paths` key or a package.json `imports` key;
      - the name of a symlink or a package that holds one.
      - a key's path (`messages/` and a key's name). An import of one that nothing resolves is the output's, unresolved, which a check reports whatever names it.

      Or else it must hold what may spell a specifier otherwise. A specifier is a string right after `from`, `import`, `import(` or `require(`, so that is a comment there, an escape in one, `\u` anywhere (an identifier may spell `require` with one), a load by anything but one whole string, or a glob.

      Or it must hold what may lead outside the listed sources, where the reading follows a module as it follows any, and that module may pass the output on unseen (`code/outside.ts`):
      - an absolute path to an entry of the system's root, or a `file:` URL;
      - a path that climbs out of its root, by its own segments `..`: a relative one from its file's directory, and one through a mapping with `*`, which starts with its key, from its target's directory;
      - the name of a directory the listing leaves out, a mapping key whose target is outside the listed sources, or a symlink to outside them.

    - An installed package is no source, so the test never sees what it holds (`code/installed.ts`). A file imports one by a specifier that starts with its name, so a left-out file's specifiers that start with an installed package's name are resolved from it and followed, as reading it would. A file that writes one whose module passes grai's on is read.
    - A tsconfig's `baseUrl` maps any specifier that is not a relative path to below it, so it is a mapping of `*`.
    - The test is necessary, not sufficient, so the reading it gives is the full reading's. On app B and the synthetic project, the reads, reaches and unresolved imports are identical with it and without it.
    - Barrels are found as files are read, until they name no more files. A workspace package outside the project is a barrel when any of its files passes the test. The names only grow, round by round, so a round tests the files left out by the names found since alone (`code/text-test.ts`).
    - Some mappings may name the output or a module outside the listed sources from any specifier: a Vite alias that is a pattern, a `*` key that maps to one, such as a `baseUrl` outside the roots, or a tsconfig that does not read. Then every file is read.
    - App B's check reads 2,269 of its 8,971 sources (25%), as the test takes each file's specifiers. The synthetic project's reads all of them, since every component imports the messages.
    - A source left out is not parsed, so its parse errors are not reported. It reads nothing of grai's, broken or not, and `check --fix` goes ahead without it.
    - **`find` and `rename` read, for their key, only the sources whose text may read or reach it** (`code/key-candidates.ts`). That is the key's name whole, or what names a module that holds it: `messages.js` or `keys.js` by a path segment that ends the path, a barrel that holds the key, or a mapping, symlink or package that leads to one. A key's path through a mapping to `keys.js` names that key's module alone, so another key's path is no name. For 100 keys on each project, find's reads, edits, bindings and reaches are identical to a reading of every file. App B reads 525 of its 8,971 sources for a key on average. The synthetic project reads all of them, since each imports a barrel that holds every key.
      - A source left out cannot read the key, so its parse errors and its unresolved imports of another key's path do not stop a `find` or a `rename`, as they do not stop `check --fix`.
    - **Only the imports that may name what holds grai's are resolved** (`code/resolved.ts`). An import whose path writes none of the round's names, and leads nowhere outside the listed sources, names a module that holds nothing, as a source that fails the test does. The reading takes such a module for one that holds nothing (`unnamed`), and resolves it once a later round's names may name it. On app B, a warm `find` resolves its imports in about 0.1 s, against 0.25–0.3 s for all of them.
  - **Svelte parses a component's template alone.** Its own preprocessor blanks each script's content, keeping every offset, and oxc parses the scripts. Svelte's parse otherwise runs each script through acorn too, which was most of its time: 2,000 of the synthetic project's components took 1.55 s, and now take 0.3 s.
  - **One pool reads the files and then resolves the sources' imports, in tasks the first free thread takes, the main thread included.**
    - The main thread takes tasks alone at first. It starts workers once it has taken a worker's start, about 0.25 s, and stops taking tasks once a worker answers, so that no worker waits on it.
    - **The pool is sized by the work, at the main thread's fastest pace after its first task**, which loads the parsers, as a fresh process's first tasks run before its code warms up.
      - A worker costs about four of its starts in all: its start, loading its code and warming up. That is about a second of CPU each on app B, so the pool takes one worker for each second of work left.
      - More workers made no run faster on this machine: app B's reading took 1.5 s with four and 1.9 s with sixteen, and twice the CPU.
    - On one thread, reading app B's 9,000 files takes 3.8 s and 5 s of CPU, and the synthetic project's 4.2 s. That is the floor of a cold run: main's whole check takes 2 s of CPU, as it reads no code but text.
  - **Each file's facts are kept on disk, in the outdir's `.grai/` state, which Git ignores already, so a one-shot command reads again only the files that changed.** The facts are cached, never an AST.
    - They are keyed by the content's hash, the hash of grai's reader code and the parsers' versions, so a change to any of them reads the file again. Hashing the reader's code, not grai's version, also covers an unreleased change to it.
    - They are written atomically, after a command that read a file again or found one gone, and an entry for a file gone is dropped then. A warm run writes nothing: on app B, writing the cache took 0.6 s of a warm `check`.
    - A command keeps the entries of the files it leaves out unread and of those outside its roots, so that a command that reads fewer files, or under a folder, costs the next one nothing. An entry for a file changed is replaced when a command reads it.
    - They are a line per file, its facts as JSON, which V8 reads back in 0.35 s for app B's facts, against 0.63 s for its own serializer's 75 MB. A save writes each entry again as it was read.
    - A module's uses are kept by what they start from, and a reading parses only those of what holds grai's. They are 70% of app B's facts, and about 6% of them start from grai's.
    - **A warm run reads only the files that changed, known by their stat** (`code/listing.ts`). The listing in `.grai/files` keeps each file's size, modification time, change time and inode, its text's hash, and what the text test needs from its text: the specifiers it loads, and whether it may spell one otherwise. A file whose stat is the one kept is taken as unchanged, and its text is read only if a reading asks for it. A tool may set a modification time back, but never a change time.
      - Git's rule for a racy entry keeps that exact. A file changed within two seconds of when it was read (a FAT volume's resolution, the coarsest a system keeps) may change again with the same times. So the next command reads it by its content, and takes it on its stat after that.
      - So the text test tests each file's specifiers, not its whole text. A file names a module only by a specifier, unless its text may spell one otherwise, which reads it. A name in a comment or a string reads no file now.
      - On app B, statting the 8,971 files takes 37–52 ms, against 228–245 ms to read them, and the first round's test takes a few ms instead of about 0.2 s.
      - A fresh checkout gives every file a new stat, so CI reads each file's text and takes its facts by its hash, from the facts it keeps.
    - A cold run costs what reading every file exactly costs, and the pool keeps that as low as it can.
    - In memory, the facts are also kept across a watch, between `check --fix`'s fix and its check, and across a build's rebuilds.
    - **A build keeps its modules' facts with the CLI's, by their code's hash** (`code/build-reading.ts`). A module whose code is the file's, as a source's is before other plugins, shares its entry with `check`, so a build after a check, or a second build, parses no unchanged module. A build lists no files, so it keeps every entry it found and drops none; a command that lists them drops a file gone. On the build bench's project, a build with its facts kept takes 0.80 s against main's 0.83 s, and one without them 1.05 s against 0.95 s.
  - The bench's projects have to resolve as real ones do. The synthetic project gets a package.json `imports` and an `i18n` module that re-exports `m`, and app B's copy keeps its package.json and tsconfig, since a guessed import is no longer read.

## CLI

- `grai compile` writes the output once; `grai watch` keeps it current, incrementally.
- `grai check` runs every compile check (lockstep, plural categories) without writing, and adds four of its own:
  - keys no shipped code reads. check reads the code as the bundler does (`src/code/`): each JavaScript, TypeScript, Svelte, Vue or Astro file or MDX document under the project, or under `--source`, outside dependencies, build output and the outdir, through its own parser, and each import followed through the module graph to grai's output, resolved by the project's Vite aliases, tsconfig paths and package.json `imports`. A key is read when a read by its name reaches it, or a read that may reach more keys than one may: a computed read reaches the keys its index can be, `m` used whole every key, a module object used whole the keys its exports hold, and a load by a template the keys whose path it matches. A load by a path the code computes (`import(path)`) reaches none, as the bundler bundles nothing for it: an app that runs the output unbundled and loads a key's module by a path it builds at run time is the gap, which the guide names, and `check --fix` lists every key it removes. The output is compiled first when it is missing, as the code's imports resolve only then. A file that does not parse is an error (`source-invalid`), as it fails the bundler, and so is an import whose path is the output's that nothing the project declares resolves (`import-unresolved`); `check --fix` removes nothing while either stands;
    - **a test ships nothing, so a key that only tests read is unused,** and the report names those tests, which must change with it. Tests are the files the config's `tests` globs match, by path from the root: by default Vitest's and Jest's names (`*.test.*`, `*.spec.*`), Jest's `__tests__` folders, and the root's `test` and `tests`. A folder named `tests` deeper down may ship, as a SvelteKit route at `src/routes/tests/` does, and calling its keys unused would have `--fix` delete them. `[]` makes no file a test;
  - inputs one locale shows and another never does: a placeholder a translation lost or invented. An input a locale only chooses a variant by, such as the gender French agrees `invitée` with, is that language's grammar, and another locale need not read it; an `input gender` declared only to quiet the check would prove nothing.
  - each place code reads a key no catalog has, `m.foo`, `m["foo"]`, a key's path or a named import of keys.js, with the `grai add` that adds it. TypeScript sees these only in TypeScript; in JavaScript and in a Svelte or Vue template such a call ships as a call of nothing. A Vite build fails on the same places, reading each module with the same reader before any other plugin transforms it (`vite-reads.ts`), where Rolldown only warns that a namespace's member is undefined (it fails a named import of one already). The build sees two kinds of code that check does not: a virtual module's, and code an earlier plugin added, such as an auto-imported `m`, unless that plugin writes it to a file.
    - Only grai's own output counts: an import is grai's when it resolves to the output's messages.js or keys.js, or a key's path that the app maps to keys.js, followed through re-exports. A named import from a module of the app's that is also called `keys`, such as a test helper, is not one of keys.js.
    - Reads are placed by scope, as the bundler binds names: `rows.map((m) => m.id)` reads its parameter and not the namespace. Comments, strings, JSX text and escapes are the parser's, so `"m.title"` in a string is no read and `t\u0069tle` is `title`.
    - `find` lists every read of the key and each use of a name such a read binds, and each read that may reach it without naming it. `rename` edits the places the code spells the key's name: a member, a string, a key's path (written out plainly where it has escapes), a named import or re-export, and a binding named after the key with every reference, writing a shorthand out in full (`{ title }` becomes `title: heading`, Svelte's `{title}` becomes `title={heading}`, Vue's `:title` becomes `:title="heading"`). A name a module gives the key (`export { title as heading }`) is that module's, so it and its importers stay. `rename` refuses only where a read may reach the key without naming it, where a binding's new name is declared in its scope or would be captured, and where the new name is another key's, naming the place.
  - each import of keys by name from keys.js, where package.json `imports` gives each key its own path (`key-path-bypassed`): a mock of a key's path reaches only the imports by that path, so an import from keys.js keeps the real key where a test mocks it. An editor's auto-import writes these. TypeScript 6's tsserver and TypeScript 7's language server (7.0.2) both offer keys.js for a key, as TypeScript sees one module for every key's path. Excluding keys.js with `autoImportSpecifierExcludeRegexes` offers a path without the key, `#i18n/messages/` in 7 and `#i18n/messages/.js` in 6. Only a declaration file per key, which the output rejects, would offer the key's own path. A language service plugin that rewrote the offer would reach TypeScript 6 alone, as TypeScript 7's language server loads none: its binary has none of tsserver's plugin loading (`globalPlugins`, `pluginProbeLocations`). So the rewrite is check's, which runs alike whatever editor wrote the import, and in CI. An import of the namespace reads keys.js whole, and a re-export passes keys on, so neither is one. The path is the first such pattern's that the project resolves to the key's own module from the importing file, as the build does. `check --fix` writes each import as one per key from that path, keeping a type import, the name it binds, the quotes and the semicolon; one with a comment inside stays as it is, and check reports it still.

  It also lists, per locale, the keys still untranslated: those whose message equals its seed, but the keys `identicalToBase` lists. This is a report, not an error, since a text can rightly read as the base locale's. `--json` prints the problems and the untranslated keys for scripts.
- `grai seed <locale>` gives a locale's catalog the base text of every key it lacks, and creates the catalog if there is none.
  - **A key the locale takes from its fallbacks is not seeded.** It is translated already, and a seed in the locale's catalog would stop it following theirs.
  - **Every key is in every locale, so an untranslated message is a seed, and equality to it is the marker.** Nothing is kept beside the catalogs.
  - **A message that rightly reads as the base text is listed in the config, under its locale in `identicalToBase`.** The report proved noisy without it: on app B it named 319 messages in one locale and 108 in another, each equal to the base on purpose (units, codes, words both languages share).
    - The list is in the config, not in a file beside the catalogs or as markers in them, so the catalogs stay the inlang format and every exception is in one reviewed place.
    - `check` and `export` take a listed key as translated, and `check` reports one that no catalog has or whose message is no longer the base text. A stale entry would otherwise hide a key that needs translating.
    - `rename` and `check --fix` change the list with the key, through the catalogs' one writer: only the list is written again, in the config's layout, and every other byte of the config stays.
  - A seeded plural keeps the variants the locale can choose, and its `other` becomes `*` unless a `*` already covers the same branch of the other selectors: a `*` for one gender says nothing of another's counts. It then compiles in a locale with more categories, such as `few` in `ru`. Each seed is compiled in the locale before anything is written, so a seed never leaves a catalog that fails.
- `grai export <locale>` prints a locale's messages for translators, or only the untranslated ones. `grai merge <file>` writes the translations back into the locale's catalog.
  - **A key the locale takes from its fallbacks is translated, in their words:** its unit's target is the message it compiles from, as `check` reads it. `--untranslated` leaves it out, a merge of it unchanged writes nothing, so the catalog stays sparse, and a new target gives the locale its own text.
  - **The file is XLIFF 2.0**, the OASIS standard translation tools exchange, and both Weblate and Phrase read it.
    - A placeholder is a `<ph>`, and a pair of tags is a `<pc>` around its words, or an `<sc>` and an `<ec>` where it crosses another pair, so a tool keeps a translator from breaking either.
    - **A code's id names one code in all its message's units:** the same placeholder or tag pair, written alike, has the same id in each, and one written otherwise, such as `{amount :number}` beside `{amount}`, has its own. A translation's own codes are the message's too. An id by name alone would let a merge swap one variant's formatter for another's, or the base's for the translation's, and say nothing.
    - CSV, which every tool also reads, holds placeholders as text a translator can mistype, and has no plurals.
    - `--json` writes the same units for scripts, with each code as the catalog writes it, since Node reads no XML.
  - **A plural is one unit per category of the target locale,** each with a note of the counts it is for.
    - Each starts from the base text for the same counts. For `ru`'s `one` (1, 21, 31…), English gives both `one` and `other`, so the unit starts from `other`, which shows the count.
    - A translation may place any code of its message.
    - A row that does not tell counts apart, such as `count=0`, stays one unit.
  - **Once a locale has a message of its own, its units follow its selection,** which may tell apart what the base's does not, such as the gender French agrees `invitée` with, or nothing the base's does, as in a language without plurals. Each still starts from the base text for the same keys. A row the locale writes and the base lacks, such as German's `count=1`, is a unit too, so a merge never drops it.
  - **`merge` refuses a unit, never the file.** A unit made from a base text that has changed since is stale, and one that places a code its message lacks, or that the file gives twice, is invalid.
    - A message must still compile and show the base's inputs; one it only chooses by is the locale's grammar. A plural needs every form, from the file or from its current translation.
    - A message no unit changes is left as it is written, and the rest go to the catalog in one write.
    - A merged message keeps the shape of the locale's own message, or of the base's when it has none: a pattern stays a pattern, and a message with declarations keeps them, with selectors or without.
    - **Its declarations are the translation's,** which the forms no unit changes read, such as a price the locale formats in its own currency, **then each of the base's it lacks,** which a code a unit takes from the base may read. Taking the base's alone would reformat the locale's own forms, and the translation's alone would refuse a unit whose source reads a local the base has added since.
  - **Machine translation is not grai's.** grai fetches nothing, and a provider, its key, its prompts and a glossary are each app's choice. A script exports `--json`, translates, and merges, and the merge's checks refuse an answer that breaks a placeholder or a plural.
  - **A key's description for translators is a note of its units,** from the file the config's `descriptions` names: whether "Open" is a verb or a state, which no source text says.
    - The file sits beside the catalogs, not in them: Paraglide reads every key of a catalog but `$schema` as a message, so a description there would break the catalogs it reads. Not in the config either, as `identicalToBase` is: descriptions are many, and copy, not settings.
    - `grai import` fills it from FormatJS's descriptors, and refuses an import whose sources describe messages when the config names no file, rather than drop them. `rename` and `check --fix` keep it in step with the catalogs, and `check` reports a description of a key no catalog has.
  - The XML reader reads only what this XLIFF needs, and strictly: no DTD, no entities beyond XML's five and numeric references. A tool's comments, CDATA, groups, segments, notes and metadata are read past or joined.
- `grai add <key> --en "…" --de "…"` adds a key to every catalog that lacks it, at once: a new key to every catalog, or one some locales lack to theirs. It refuses unless a text is given for each locale that lacks the key and for no other, so it never overwrites a message.
- `grai import --from i18next|icu <file or dir>…` converts another library's catalogs into the project's catalogs, for a migration. Each source file's locale is its name (`en.json`) or its directory's (`en/common.json`).
  - **It writes new catalogs only, and nothing at all on an error:** an unreadable source, a file whose locale is unclear, two source keys that become one key, or a catalog that exists already. A migration then never overwrites edits.
  - **A message that cannot be converted in one locale is left out of every locale,** so the catalogs compile, and the report names it, its locales and why. The report also names what renders differently. A partial conversion would otherwise ship as a missing key or another locale's words.
  - **A key a locale's source lacks comes from its fallbacks when one along them has it,** as compiling reads it: the locale's catalog is written without it, so it keeps following them, and the key is not left out.
  - **An ICU message is read by intl-messageformat's grammar,** the one next-intl and react-intl render with, not by a looser one: its identifiers and Pattern_White_Space, its exact keys, styles and tags, and a `}` outside every argument as text. A message it rejects is left out as not valid, saying what is wrong, so an import never ships text the app could not have rendered, and never reads a typo, such as `=1.0`, as something else.
  - **An i18next message is read in i18next's own passes, by its own patterns:** `{{-name}}`, then `{{name}}`, then `$t(key)` in the text they leave, so a brace, a dash or a parenthesis means to grai what it means to i18next. A placeholder whose name holds another's value is left as written, as i18next leaves it, since no call passes such a name. One that i18next would fill at an earlier copy of its text is left out.
  - **A key is its source path joined by `_`,** every character an identifier cannot hold as `_`. When a locale's directory holds several files, each key starts with its file's name, i18next's namespace.
  - **A plural is MessageFormat 2's `local nPlural = n: plural`, and an ordinal (ICU's `selectordinal`, i18next's `_ordinal_` forms) `local nOrdinal = n: plural type=ordinal`.** ICU's and i18next's `other` becomes `*`, because both take it for any count the other forms do not cover. An exact `=0`, and i18next's `_zero` in a locale without a zero category, becomes a choice on the input itself, written before the category, as both libraries try it first. A category the locale does not have is dropped, since neither library ever chooses it.
  - **Nested and sequential choices become several selectors, outermost first,** so MessageFormat 2's preference picks what ICU picks.
    - **A choice on an input that a choice before or around it already chose on joins the same selection.** Each way the message reads needs, of each selector, the key its choice took, or for `other` none of that choice's keys, and two ways that need what no value gives never read together. ICU allows the repetition, as in `{n, plural, one {# cat} other {# cats}} {n, plural, one {is} other {are}}`, and writing one choice around the whole sentence instead would make translators repeat it.
    - **A way is written with the keys it needs and `*` for the rest.** That reads right while each choice's selectors come before those of the choices in its options. A repeated choice can break this, as one on `n` inside another's `other` can. The import checks every value the selectors can take, and where one would be read wrong, it writes each way once for every key the message names of each selector, so that `*` stands only for values no key names. A message that needs it gets more variants, but no other message changes.
  - **A plural's `offset:n` becomes an `:offset` local of the count less `n`,** which its categories choose by and its `#` shows, while its `=n` keys still compare the count itself, as ICU reads them: "You and # others" is `local countOffset = count: offset subtract=1`. An ordinal's offset, which needs the ordinal rules on the moved count, is left out.
  - **A formatted value is formatted alike.** ICU's `#` becomes `{n :number}`. Its `number`, `date` and `time` arguments become `:number`, `:integer` and `:date` or `:time` with the Intl options of intl-messageformat's styles. i18next's `number` and `datetime` become `:number`, and `:datetime` with their options, or `:date` with Intl's default fields when no option chooses them. Its `currency(EUR)` becomes `:currency currency=EUR`, or `:number style=currency` when it passes an option `:currency` does not take; `relativetime` becomes `:relativetime` with its unit, `day` as in i18next; and `list` becomes `:list`. Each call is checked as the compiler checks it.
  - **A message and a plural's forms that would become one key are left out,** as `title` beside `title_one` and `title_other` would: i18next calls the message without `count` and the forms with it, so one key would lose one of them. The report names both, for the source to rename one.
  - **i18next's ordinal forms become a key of their own, ending in `_ordinal`,** since i18next calls them by the plural's key with `{ ordinal: true }`. The report names each, so the call can move to the new key.
  - **An ICU skeleton is read as intl-messageformat reads it,** into Intl options, then written as the call those options make: `{price, number, ::currency/EUR .00}` is `{price :currency currency=EUR fractionDigits=2}`, `::percent` is `:percent`, `::unit/…` is `:unit`, and `{d, date, ::yMMMd}` is `:datetime year=numeric month=short day=numeric`. An option the function does not take, such as a sign on a unit, gives `:number` with the style instead.
  - **What grai cannot express is left out, never approximated:** an ICU currency style without a currency, a skeleton stem or date field Intl has no option for (`scale`, `integer-width`, `w`), an ordinal's `offset`, a format a project adds to i18next, nested values, and `$t()` with options or of a message with inputs. `$t(key)` of a text is inlined.
  - **Three differences are reported, not left out:**
    - an i18next plural that lacks a locale's form shows its `_other` text, where i18next showed the key's name;
    - i18next escapes the values of `{{name}}` and of a list for HTML by default, and grai gives them as they are. Escaping belongs to whatever shows the text: React, Vue and Svelte escape it, and an escaping message would show `&amp;` there, or in a native view. Every such message is reported, so code that set i18next's text as HTML can escape the values first. `{{- name}}`, numbers and dates are not reported.
    - i18next fills `{{name}}` in the text its pass for `{{- name}}` left, so a `{{…}}` in such a value is filled in too. A value only comes at run time, so a message compiled ahead of time cannot do that; grai gives the value as it is, and reports each message with a `{{- name}}`.
  - `bench/import-equivalence.mjs` renders every imported message with grai and with i18next or intl-messageformat, for each locale and a range of inputs, i18next with its escaping off and then on, over values with HTML in them, and fails on any difference the report does not name. The libraries are the bench's dependencies, not grai's.
  - `bench/import-fuzz.mjs` imports thousands of generated messages full of each syntax's special characters, and fails unless each renders the same in grai and in the library, or is left out: as not valid only when the library rejects it too, else with the reason grai cannot express it.
- **`find`, `rename` and `check --fix` read the sources through check's scan:** the same files, and the same notion of a name a source writes. None parses JavaScript, Svelte or Vue. On a synthetic project of app B's size, 13,000 keys and 9,000 files (68 MB), `find` takes 0.24 s, `rename` 0.46 s and `check` 0.80 s, and `check --fix`, which checks after it removes with the sources it read, 1.1 s (`bench/refactor.mjs`, load 4–5).
  - **A command that changes or deletes acts only on evidence it can establish, and refuses, with the reason, where it cannot.** The text does not show scope or values, so where reach or ownership is uncertain, `rename` refuses and `check --fix` keeps the key; neither guesses.
  - A call site is `m.key`, `m?.key`, `m["key"]`, a per-key import's path and name (static, dynamic or destructured), or a use of the name that import binds. `m` is any local name an import of `m` binds, whatever the path, so a re-export through the app's own module counts, and so does `import * as` keys.js, and `messages.m` after `import * as messages` of messages.js.
  - Tests are sources here too: `find` shows their call sites, and `rename` changes them, so a renamed key's tests keep passing. Only `check` and `check --fix` set them aside, to judge what ships.
  - `grai find <key>` prints the key's line in each catalog, each call site, and each other place a source writes the name.
  - `grai rename <key> <new>` renames the key in every catalog and at every call site, then compiles. It changes nothing when any other place writes the name (an object key, a string, someone else's property), and names each, since only the author knows what it means. A new name another key has, ignoring case, or one a file that binds the key already uses, refuses it too. So does a read by a computed name that may reach the key (`name => m[name]()`), and a file that reaches the key through a name it also declares as a parameter or local (`function render(m)`), since which `m` each use reads is a matter of scope.
  - `grai check --fix` removes each key no source names, then checks. A key that a read by a computed name may reach stays, and the report names the read: `m[expr]`, also through a wrapper (`messages.m[expr]`, or `i18n.m[expr]` through the app's own module), `m` or a namespace import of messages.js used whole, or per-key modules loaded by a built path. A read's literal start narrows its reach only when the index is a template that starts with text, or text joined to one name (`"promo_" + season`); anything else, such as a choice, reaches every key. A key that is no key name, such as `sign-in`, stays too: the scan finds only names, so it cannot see `m["sign-in"]`, and the check reports the key as invalid, for `grai rename` to fix.
- **Every command that writes a catalog edits its text, and every other byte stays,** so a diff shows only the change:
  - `add`, `seed` and `merge` give a key the catalog has its new value in place, and add a new key after the last entry of its object, in that object's layout: its indent, line breaks and spacing. A catalog with no entries yet, or a new one, takes another catalog's layout;
  - a new key goes where the base catalog has it, so `seed` and `merge` keep the base's objects. `add` puts it in the deepest object whose key, then `_`, starts it (`cart_tax` in `cart`), at the same path in every catalog, making the objects a catalog lacks;
  - a rename changes the key's string, and keeps its place while its object's key, then `_`, still starts the new name; else the message moves to where `add` would put the new key;
  - a removal takes the entry with the separator before it, and an object it leaves empty goes too;
  - `import` writes new catalogs, an entry per line indented by a tab.

  The files are written all or none: each new text goes to a temporary file of the writer's own, created anew beside its file so that it overwrites nothing, and they are renamed into place once all are written, each with the permissions of the file it replaces, so a script that a rename edits stays executable. A file that then cannot be replaced, such as a path that is now a directory, has the files already replaced get back what they held, so a command that fails leaves every catalog as it was.
- Every command prints each error on its own line, sorted by file, key and locale, then how many, and exits with 1. A usage error exits with 2.

## Next.js

Next runs the proxy apart from the render, renders a request's layouts and pages side by side, and renders client components on the server in a module graph of their own. `@xyrolle/grai/next` gives each of these the request's locale the way Next lets it, and a message call stays a plain function.

- **The proxy hands the locale over in the path.** `proxy` resolves it by the config's strategy, through the output's `middleware`, and rewrites the request to the same path under `/<locale>`; the pages live under `app/[locale]/`. Next's docs pass data from a proxy by the URL, headers or cookies, and the path is the one that keeps pages static: Next routes the locale as a segment, `generateStaticParams` renders each locale ahead of time, and `next/root-params` reads it anywhere. The URL stays as the strategy has it, so with `url` the base locale has no prefix, and a cookie or `Accept-Language` app has none at all.
- **A server component reads the locale from React's `cache`, which React keeps for one request's render.** Each page, layout and `generateMetadata` calls `bindLocale(locale)` with its param before any message. Measured in Next 16.4: a page and its `generateMetadata` start before the layout's `await params` returns, and a client navigation renders only the segments that change, so no single place can bind it for the others. A message before the binding throws a `GraiError` saying so, rather than rendering the base locale's words. The cache holds the request's `{ index }` record, which `setLocale` in the render changes in place.
- **Outside a render, a call names its locale** (`m.saved({}, { locale })`). React keeps no `cache` in server actions or route handlers (measured), and `next/root-params` does not reach them either.
- **A client component on the server reads the locale from React context.** Next renders client components in a module graph of their own, with no call an app could wrap in a scope, so `LocaleProvider`, in the root layout, gives the request's locale as context, and the dispatcher reads it with `use`. On the server a client component's code runs only while it renders, which is where `use` works. That record is read-only, and `setLocale` there throws: what a client component renders on the server must be what it hydrates with. Interleaved requests keep their own locales, in server and client components alike (`test/next.test.ts`).
- **In a browser the locale is the page's `<html lang>`, and the page keeps it.** Next keeps the root layout through a client navigation into another locale, since only the param's value changes. Once React has written the new `<html lang>`, `LocaleProvider` switches with `setLocale`, which loads that page: a mounted component, memoized by hand or by the React Compiler, would otherwise keep its old words. A page whose `<html lang>` is not its locale is never reloaded, so that mistake cannot loop.
- **`withGrai` points `@xyrolle/grai/next/output/*` at the outdir in Turbopack and webpack,** so @xyrolle/grai/next's modules bind the app's own runtime, one instance per layer Next bundles. Why Next resolves the output this way while SvelteKit takes it explicitly is below.
  - `next build` compiles and fails on any error.
  - `next dev` checks whether the output is current. If it is, Next starts at once, while the watch's first compile builds what each edit starts from; if not, Next waits for that same compile. Either way a start compiles once. Next asks for its config twice in one process, and the watch starts once.
  - The watch runs on a thread of its own, a worker in Next's server process, so neither its first compile nor an edit's takes Next's thread while Next compiles and renders a page. On Next's thread, a first compile with no build saved, as after a clone or an upgrade, took 222–291 ms of it for 20,000 keys, and one from the saved build 28 ms for the synthetic catalog's 6,366 keys in 3 locales (`docs/runtime.md`).
  - Any other command, such as `next start`, bundles nothing, and gets the config as it is.
- **Per-key paths need nothing from the adapter:** package.json `imports` map them to keys.js in Turbopack, webpack and TypeScript alike.
- **A module imports the messages as a namespace of keys.js,** as in Vue. In `next dev`, Turbopack takes `m.cart_title` through keys.js to the shard that declares it, and compiles no other shard for it, as the outdir declares its modules of keys free of side effects. `import { m }` from messages.js names a namespace that module re-exports, and `next dev` builds it whole, every key's binding, in each layer that imports it and again after each edit. On the Next bench's page, an edit to the server component's message then shows in 227 ms against 158, and to the client component's in 132 against 75; with app B's catalogs, in 493 against 190 and 294 against 92 (medians of 5, interleaved). Turbopack follows a member read through such a namespace when it builds for production, not in `next dev` (`docs/followups.md`).
- **A server component's messages send no code to the browser,** only the HTML they render. A client component's messages ship as their keys' functions with every locale's variants: one Next build serves every locale, and Next gives an adapter no way to point a page at one locale's chunks. Unused keys are left out by the bundler, so only the keys client code names ship (`docs/runtime.md`).
- **Each layer compiles the keys its routes read, in a few modules.** Turbopack follows `m.key` to the module that declares it and compiles nothing else of the output for it (the outdir declares its modules free of side effects), but a page's keys fall in every shard. So the watch reads the app's code once the server is quiet after its first compile (half a second in which the whole process used under a tenth of a core), with `grai check`'s reader, and saves the keys each route's side reads as groups (`next/key-groups.ts`):
  - a route is a page or route handler with its segments' files from the root down (`next/routes.ts`), and its sides are its server components and every module past a `"use client"` one, which the SSR and browser layers both compile;
  - keys the same routes' sides read are a group, and two groups are one when the modules that saves, at what a module costs Turbopack (about 2.5 ms of CPU in a layer, what about 12 KB of keys' code costs), outweigh the code compiled for nothing in the sides that read only one (`key-sets.ts`, as a Vite build's page chunks);
  - a key is read where a module takes it: a key a barrel re-exports, by name or from its own path (`export { title } from "#i18n/messages/title.js"`), counts for the routes whose modules take it from the barrel. A barrel is seen through to the modules its importers take names from, an `export *` to the branch whose module exports the name, and to the modules whose package keeps their side effects, which the bundler loads whatever is taken (`next/route-reach.ts`, as `module-links.ts` does for a Vite build). An app's own modules keep theirs unless its package.json says `"sideEffects": false`, so a route that loads a barrel of components compiles each of them, as Turbopack does. From the server's side a client component's module is a reference whose names Next's bundler does not see, so it keeps every branch of an `export *` into one: measured in `next dev`, as each of these (`test/next-dev.test.ts`);
  - the watch does not compile for the groups it saves. Every compile reads them, as `next build` does, so they apply from the next compile on: the next start's, or, in the running server, the next catalog edit's. That compile places every key anew, writing each module of keys once, and Turbopack compiles the page's modules of keys again: on the Next bench's page the first edit after the save showed in 239–277 ms, the edits after it in a median of 173 ms. Holding a running watch to the groups it started with would give it a layout other than a build's of the same state;
  - a key a component starts to read after the save is served from its shard, and grouped once the next session's watch has read the code again;
  - a start with no groups saved, as a fresh clone's, reads them beside its first compile, which Next waits for then (`next/first-groups.ts`). A thread of its own reads the code at once, keeping each file's facts in memory; the groups need the output written, as the reading resolves the app's imports of it, so they are read again, from those facts, once the compile has written it. The thread writes nothing, as the start may stop it at any point. One operation decides when Next may start (`next/startup.ts`): it waits for the first compile, then for the groups if the code was read before that compile was done and they come within its time again, stops the thread and waits for it to stop, and saves the groups and compiles once more to place the keys by them, that compile's read again of a catalog met mid-save included. A compile of an edit meanwhile releases nothing, so no output is written for the groups once Next has started, and the build saved for the next start is the one placed by them. Otherwise the groups are read once the server is quiet, as above. The rule is a heuristic, measured on the Next bench's page and on generated apps of 2,000 files: a start cannot tell what the groups save its pages, which a page that reads no key gains nothing from; the time it gives them counts any wait for the output's lock, and not the save and compile after them. On the bench's page the code is read before the compile is done: at 6,366 and 13,326 keys, withGrai holds Next back 59–80 and 118–129 ms more, and the first page comes 195–373 and 504–611 ms sooner (paired medians of 8 and 10 rounds, three windows, against main and the same start without). An app of 2,000 files takes 380–590 ms to read cold against a compile of 115–170 ms, so its first start keeps the shards, at no cost: stopping the read takes it 1.4–4.4 ms, and its first page came −37 and +85 ms against main's (paired medians, within ranges of −1,137 to +567). Its next start has the groups. A start with groups saved never reads beside its compile, so a checkout does not go back and forth between the two layouts;
  - `next build` and the CLI do not read the groups: each run would pay the read, 0.4–0.6 s cold for 2,000 files and 0.1–0.3 s more to group, for a later `next dev` on the same checkout, which reads them itself when that is cheap.
- **In dev, Turbopack watches the outdir.** An edit rewrites one shard or group in about 5 ms, and Next's own refresh takes the rest.

**Why the Next adapter finds the output itself.** The SvelteKit adapter, `handleLocale`, takes what it needs of the output from the app's hook, and that is enough: Kit renders every component of a request inside that one hook, in one module graph. Next has a graph for server components, one for client components on the server and one for the browser, and the second is reached only through a `"use client"` module. A server component cannot hand that module the runtime, because only serializable props cross into a client component. Passing it explicitly would then take two glue files in every app, one for server components and one `"use client"`, each binding a runtime instance the adapter can bind itself. So `withGrai` resolves `@xyrolle/grai/next/output/*` to the outdir in each bundler. That is the same mechanism next-intl's plugin uses for its request config, and it is the reason `@xyrolle/grai/next` needs `withGrai` in `next.config`.

`@xyrolle/grai/react`'s `Markup` draws a markup message's `.parts()` with the app's function for each element, which takes the options and attributes the message writes on it. The function decides what they do, and none reaches the page on its own: they are the translators', and an `href` or a `class` spread onto the element would hand them the page. It is React's, not Next's, so a React app on Vite uses it too, and it renders in server and client components alike. An element the message names and the app does not draw throws, naming it.

## Astro

Astro runs a request's middleware around the page's render, renders islands on the server inside that render, and builds one client for every locale. `@xyrolle/grai/astro` is an integration, so an app adds one line to `astro.config` and writes no middleware.

- **The integration does the setup:** it adds `@xyrolle/grai/vite` and the middleware, compiles for `astro sync` so `astro check` sees the types, and checks the two configs once Astro's is done. In dev, an edit reloads the open pages (`reloadOnEdit`), since Astro draws a page on the server, islands aside.
- **The middleware binds the locale around Astro's render, through the output's `middleware`.** Astro starts rendering a page inside the middleware's `next()` and streams it after, so the `AsyncLocalStorage` binding reaches every component and island the page renders. Interleaved requests keep their own locales, rendered on demand and prerendered four at a time alike (`test/astro-example.test.ts`). Paraglide's static Astro setup sets a process-wide locale per page instead, which holds only while pages render one at a time.
- **Astro's i18n routing owns the URL, and grai reads it.** grai rewrites no path: pages live under their locale's path, so a static build prerenders each locale's pages in that locale, and `getRelativeLocaleUrl` and Astro's fallbacks work as they do without grai. With Astro's routing on, the build checks that grai finds the same locale in the same URL: `url` first in the strategy; the same locales, each under the same prefix, so a `{ path, codes }` locale is its first code under `localePrefixes`; the same default; and `prefixDefaultLocale` as `localePrefix: "always"`. `getLocale()` is then `Astro.currentLocale` on every path the routing covers, and a path it leaves out is one of `unlocalizedPaths`, whose locale the strategies after `url` find. Binding `Astro.currentLocale` directly would skip that check, and the output's middleware is still needed for the other strategies. A `base` and `domains` are refused, saying what to set, since grai's URL helpers do not know either yet.
- **The middleware writes `<html lang>` and `dir`:** the browser's runtime reads `<html lang>` as the page's locale, so it must be the one the server rendered in. A layout may write `lang={Astro.currentLocale}`, Astro's idiom, and the middleware keeps it and adds the direction. It reads only the document's start, up to the `<head>` start tag, and passes every byte after it on as it comes, so a page streams as before.
- **A built page loads only its locale's words, through an import map** that the middleware writes first in the head: from `/_astro/grai/` to `/_astro/grai-<locale>/`, under Astro's `base` or assets prefix. Astro writes no `modulepreload` for islands, so the map is the whole job. With Astro's CSP on, the integration lists each locale's map by its hash in the CSP's `scriptDirective.hashes`, which Astro puts on every page. The middleware's `context.csp.insertScriptHash()` would reach no policy, since Astro gives a page its policy only once the middleware has called `next()`, and reading `context.csp` makes Astro warn on every page of an app without a CSP. Paraglide's per-locale build has to own Vite's `buildApp`, which Astro owns, so on Astro it ships every locale's words to each island.
- **A static Astro build writes each prerendered page at its paths in a locale's words too, through routes grai adds.** A static build writes only the paths a route gives, and none has the words. @xyrolle/grai/astro adds a prerendered route for each path in a locale's words, its prefix a rest parameter (`/[...0prefix]/produse/[id]`). Its `getStaticPaths()` runs the prerendered pages' own, of those whose pattern may route a path `pathnames` translates, and gives the paths in the route's words. The middleware renders the page's route at each, so Astro writes the page there, lists it to integrations as a sitemap reads them, and its dev server and its server route the words as they route any prerendered page. Its server serves a page rendered on demand through the middleware as before. Each of those pages' `getStaticPaths()` runs twice in a build, since Astro gives no other code its result. Astro names its routes only after `injectRoute` closes, so grai cannot add a route of the page itself, and a custom prerenderer is one slot, which adapters fill. Astro exports neither how it writes a path from params nor `paginate`, so grai carries copies (`astro/route-paths.ts`), which `test/astro-paths.test.ts` runs beside Astro's own.
- **Astro's own routes are left alone under `localePrefix: "always"`.** There grai sends a request without a prefix to its locale's path, and Astro's image endpoint, server islands and prerendered `/404` and `/500` have none, so the build asks for them in `unlocalizedPaths`, naming each.
- **A prerendered page fails the build when the request, not its URL, would give its locale:** a `cookie` or `preferredLanguage` strategy ahead of `url`, or one after it for a path that names no locale. Such a page would show every reader the one locale it was built in. So does one prerendered at a URL that names its locale as a file, `/ro.html`, as `build.format: "file"` writes a locale's page and `"preserve"` writes `[locale].astro`: the `url` strategy reads a whole segment, and reading `.html` off it in the runtime would change other frameworks' paths.
- **The middleware module is the project's own:** the integration writes it, importing the output's `server.js` and `runtime.js` by path and handing them to `@xyrolle/grai/astro/middleware`, since Astro has no hook file for the app to write that in. The output's functions are the app's own instances, so the middleware binds the locale the app's messages read.

## Package

- **One package, `@xyrolle/grai`.** A project installs one thing, and the adapters version with the compiler they wrap. The name is scoped because npm refuses a name this short when it is too similar to existing ones, as `grai` is. Subpath exports, each added with its code:
  - `@xyrolle/grai`: the compiler's API;
  - `@xyrolle/grai/vite`: the Vite plugin; the SvelteKit adapter comes as `@xyrolle/grai/sveltekit`, thin, taking the project's generated modules;
  - `@xyrolle/grai/svelte`: the Vite plugin for a Svelte app, whose client build also reads a call without inputs as its string;
  - `@xyrolle/grai/sveltekit/vite`: `@xyrolle/grai/svelte`'s plugin, writing each message chunk's copy per locale for SvelteKit's pages;
  - `@xyrolle/grai/sveltekit/client`: in dev, a catalog edit drawn again in place, imported for that alone;
  - `@xyrolle/grai/next`, `@xyrolle/grai/next/config` and `@xyrolle/grai/next/proxy`: the Next adapter, also thin, which finds the project's generated modules through `withGrai`;
  - `@xyrolle/grai/react`: the `Markup` component;
  - `@xyrolle/grai/astro`: the Astro integration, and `@xyrolle/grai/astro/middleware`, the middleware it adds;
  - `@xyrolle/grai/vue`: Vue's `Markup`, and `@xyrolle/grai/vue/client`, which renders an edit again in place in dev;
  - `@xyrolle/grai/nuxt`: the Nuxt module;
  - the `grai` binary: the CLI.
- **Node 22.18 or later.** The compiler needs 22.12, Vite 8's floor, but the floor is the oldest Node the tests run on, and they start Node on the TypeScript sources, which 22.x runs without a flag from 22.18. CI runs them there, on the LTS and on the current release, on Linux, macOS and Windows.
- **The output has no dependencies, and the package two: its parser and its resolver.** The generated output needs only the platform, and `AsyncLocalStorage` on the server. Each locale's text direction is worked out when grai compiles, so the runtime looks it up by index. The compiler needs only Node; every reader of code needs `oxc-parser` and `oxc-resolver` ("Reading code"). Vite, Svelte, magic-string, Next, React, Astro, Vue and Nuxt are optional peer dependencies of the adapters that use them, as SvelteKit will be of its own. Svelte's, Vue's and Astro's packages also read their components, and MDX's is an optional peer for reading MDX documents, each with its own parser.
- **The docs site is Starlight, its pages written from the README and `docs/` at each build,** so each fact has one source. A page ships 3–5 KB of JavaScript gzipped, against about 62 KB for VitePress's Vue app, and the site runs on Astro, which grai has an integration for. VitePress installs in half the space (100 MB against 204 MB) and builds faster (2.7 s against 4.3 s). Starlight's links validator fails the build on a link to a page or heading that is not there, as VitePress does by default.
- **The changelog is written at release, from the commits since the last tag,** not by each pull request: two open pull requests that both add a line at its top conflict, and a conflicting pull request is replaced, not merged.
  - Changesets avoids the conflict with a file per change, at the cost of a dependency and a step in every pull request, for one package with one releaser.
  - pnpm's own change intents, tried with pnpm 12.15, did not bump 0.0.0 on a minor change and wrote the changelog under `.changeset/changelogs/` rather than `CHANGELOG.md`.
- **A publish runs the whole gate first** (`prepublishOnly`), so nothing reaches npm that CI would fail.
